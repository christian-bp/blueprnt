# CLAUDE.md: project rules for blueprnt

Project-specific rules for agents and developers. Add rules as needed. Keep them short and absolute.

See also: `AGENTS.md` (Next.js version warning + agent-skills config) · `docs/PLAN-V1.md` (the plan) · `CONTEXT-MAP.md` + `docs/contexts/` (domain glossaries) · `docs/adr/` (architecture decisions, read before changing architecture).

## Language

- **All code, code comments, log messages, commit messages, and code filenames are in English.** This file too. (Swedish domain documents under `docs/` keep their Swedish filenames; they are content, not code.)
- **Domain documents are in Swedish:** `docs/PLAN-V1.md`, `CONTEXT-MAP.md`, `docs/contexts/`, `docs/adr/`.
- UI copy lives in the i18n message files; English (`en.json`) is the source locale.

## Writing style

- **Never use em dashes (" — ")** in text we write: UI copy, documents, comments, commit messages. Use a period, comma, colon, or parentheses instead.

## i18n: never hardcode text

- **All user-facing text goes through i18n** (`next-intl` + `@workspace/i18n`). NEVER write display text directly in pages/components, not even "temporarily".
- New strings are added to **`packages/i18n/messages/en.json` first** (English is the base; the `Messages` type is generated from it), then mirrored to **every other message file in the same folder** (which locales exist is governed by `routing.ts`). The type system catches keys missing from `en`; the parity test in `packages/i18n` catches keys missing from the other files.
- **Everything we build must work in every configured locale, not just English.** Whatever the app renders for users must exist and behave correctly in every locale `routing.ts` lists (currently en, sv, nb, da, fi): not only UI strings, but also seeded and template content (e.g. the industry starters) and any AI-generated text. A feature is not done while a language only works by falling back to English. New or machine-generated locale content is a draft: flag it for native review.
- **Every Next.js app must contain `i18n-env.d.ts`** (the three-line shim importing `packages/i18n/src/i18n`). Without it, typed translation keys are off in that app and unknown keys fail only at runtime.
- Key naming: dot namespaces per context (`web.*`, `dashboard.*`, `accounts.*`, `model.*`, `assessment.*`). Domain-term keys are defined in the glossaries' i18n tables. Parent/leaf conflicts are resolved with a `label` sub-key.
- **Internal navigation always uses the Link component** (`next/link`, or `@workspace/i18n/navigation` Link where the locale is involved), never plain `<a>`. shadcn blocks generate framework-agnostic `<a href>` tags; swap them during adaptation.
- The backend (Convex) returns **error codes/keys, never display text**. The frontend translates.
- **AI-generated text is always in the user's CURRENT DISPLAY LANGUAGE** (the active next-intl locale passed from the client), never the org's stored default. Every AI generation action takes the caller's `locale` and uses it for the prompt's output-language instruction AND any localized prompt content (e.g. track names). The prefill is the canonical example: it resolves `promptLocale(locale, settings.language)`.
- Machine-translated message files are drafts. Flag new translations for native review.

## Domain language

- Use the glossaries' canonical terms (`docs/contexts/*/CONTEXT.md`) in code, issues, and commits. Code identifiers in **English** (the code term in the glossary), domain documents in **Swedish**.
- **Level 1 = highest.** Track = kind of job, set on the role; Seniority = the individual's seniority within the track (V2, never on the role; ADR-0005); Level = computed weight; Step = one of a criterion's 0-5 anchor steps. Never conflate them. (ADR-0014 renamed the terms: the computed weight was Band, the individual's seniority was Level, the anchor scale's positions were levels. Older ADR bodies keep their original wording.)

## Architecture invariants (never break without a new ADR)

- `packages/core` is **pure and deterministic**: no Convex/Next/React imports, no side effects, no non-determinism (no clock, network, or randomness in its logic), so the engine runs identically on client and server. Score/level are always derived by the engine and never stored (ADR-0002). "Pure" does **not** mean dependency-free: a pure, deterministic, side-effect-free dependency is fine, and a well-tested library is preferred over reinventing it. The invariant is no framework coupling and no side effects, not an empty dependency list. This purity requirement is specific to `packages/core`; it is not a repo-wide rule.
- **AI never touches the deterministic score/level path** and never auto-decides. AI output is a suggestion with provenance that HR confirms (ADR-0003). AI calls happen only in Convex actions, only against EU-hosted models.
- **Never send personal data to the AI.** Prompts carry only role-level and organization-level content (job profiles, criteria, the model, company context such as industry, country, size). Never include an individual's name, salary, performance, contact details, or any other PII (Role ≠ Person; GDPR). A feature that would need person data to prompt does not call the AI.
- **Role ≠ Person:** the `role`/`rating` tables must never carry person, salary, or performance fields. Role ids are permanent and never reused.
- **Weights are 1-5 weight points under a fixed point budget** (criteria count x 3, exact sum; ADR-0004). Percent shares are derived display values; free percentages or arbitrary weight numbers are never entered. Role scores are normalized to the fixed 0-100 scale.
- Every Convex function is **org-scoped** (tenant isolation). No level override.
- **Every state-changing mutation writes an audit row** via `logAudit` with an `AUDIT_EVENTS` key (`lib/audit.ts`). `logAudit` also maintains the audit count/offset aggregates (`lib/auditAggregates.ts`, two `@convex-dev/aggregate` instances) that give the log's pager its exact total and O(log n) jump-to-page; they store only namespaces and `_creationTime` keys (no PII), `devReset` clears them, and convex-test registers them in `initConvexTest`. Adding a new auditable operation means adding its event key (`lib/audit.ts`), a payload entry in `AuditPayloads` (compile-time-guarded), AND a readable label under `dashboard.auditLog.events` (platform events: `dashboard.admin.auditLog.events`) in every locale, or the log shows the raw event key; the audit-label coverage test (`apps/dashboard`) guards the labels. **A new event also declares its category and its subject, and its payload carries its entity's id.** Category (the app AREA: model/role/pay/...) derives via `categoryForEvent`; a backend test fails on an event without one. Subject (the entity INSTANCE the event is about: `{ kind, id }`, internal ids only, never PII) derives via the compile-time-total `AUDIT_SUBJECTS` map (`lib/audit.ts`): a new event does not compile until it declares a subject deriver or an explicit reviewed `null`, and the payload must carry the id of the entity the event is about at write time, because a row written without it can never be backfilled. Subject kinds (today `payMappingRun`, `role`, `person`) are added only when a retrieval question exists. The `person` kind exists for ERASURE, not for browsing (ADR-0013): person diffs record the employee's own identity values, so a hard delete must be able to find every row about the person and tombstone them, which an indexed subject makes bounded and a payload scan would not. `anonymizePersonAuditRows` is its only consumer; no product surface reads any subject yet. The field is populated from day one so every row stays attributable forever; the `by_org_subject` index and the search index's subject filter fields are in place for the coming consumers (a per-run history view, the export slice). **A new audit CATEGORY wires its whole surface in the same change:** the `AUDIT_CATEGORIES` (or `PLATFORM_AUDIT_CATEGORIES`) value, the `categoryForEvent` mapping, the dashboard filter lists (`AUDIT_FILTER_CATEGORIES` / `PLATFORM_AUDIT_FILTER_CATEGORIES` in `apps/dashboard/lib/audit-detail.tsx`, drift-guarded against the backend constants by `audit-labels.test.ts`), and the `dashboard.auditLog.categories.*` (platform: `dashboard.admin.auditLog.categories.*`) labels in every locale. The people/pay areas once shipped without their filter options because nothing enforced this; the drift tests now do. Result-affecting changes additionally log a `level.shift` diff. **The audit-log detail (table cell AND detail sheet) always renders labeled, human formatting, never a raw payload `key: value` dump.** A `changes` map renders through `formatChanges`/`changeEntries` (before/after rows); a flat-stats payload (counts/codes with no `changes` map, e.g. `people.imported`, `classification.suggested`, `platform.userDeleted`) renders through `payloadStats`/`formatStats`/`StatList` (`lib/audit-detail.tsx`). **Every payload field (a `*_AUDIT_FIELDS` diff field or a flat-stat) resolves via `fieldLabel` to a `dashboard.auditLog.fields.*` label in every locale**, so no surface ever shows a raw key. **A payload field whose VALUE is itself a coded/enum string (a scope, a verdict, an area key, a reason code) renders through a localized value label too, never the raw code.** `resolveCodedValue` (`lib/audit-detail.tsx`) is the typed resolver (one `Record` per coded domain, so a value added to the domain without a label is a compile error); prefer reusing an existing domain label (e.g. `dashboard.payMapping.*`) over inventing new `dashboard.auditLog.values.*` wording for a concept that already has one elsewhere. A new coded field ships its value labels, reused or new, in every locale, in the same change as the field. Prefer modeling a before/after change as a `changes` diff (not two flat scalars) so it renders as an arrow, and never diff a raw internal id with no display value (log a marker instead). The field-label coverage test (`audit-labels.test.ts`) imports the backend field-set constants and fails if any field lacks a label; a new auditable field ships its label, in all locales, in the same change. Scope: this governs user-initiated changes to auditable domain state. Append-only telemetry logs (e.g. AI usage events in `ai/usage.ts`) are outside it: they are not user-initiated domain changes and the event table is itself the record. The trail records role/org/model domain content (which may include role-level free text such as motivation, purpose, and responsibilities). It also records the employee's own identity values in `person.*` diffs (name, gender, employee number, birth date, job title; ADR-0013), because a pay-mapping audit has to show what changed on a person's record and a diff that dropped those fields wrote empty rows for the most common edit there is. That is lawful only together with its erasure path: `anonymizePersonAuditRows` tombstones every identity value and rebuilds the derived `searchText` across the person's whole trail on erasure, so no direct identifier survives a hard delete (what remains is the pseudonymized structural residue, kept on the legitimate-interest basis; ADR-0013 states the claim precisely, do not upgrade it to "no person data"). Whether a person field is identity or structural is declared in the compile-time-total `PERSON_AUDIT_FIELD_KIND` (`lib/audit.ts`), so a new person field does not compile until it is classified, and because the scrub only reaches rows carrying a `person` subject, **an identity field must never enter another event's diff** (a test crosses the identity fields against every other `*_AUDIT_FIELDS`). Salary amounts, performance, and contact data still never enter the trail at all (Role != Person).
- All data stays within the **EU** (Convex eu-west-1; ADR-0001).
- **A person is erasable; keep PII minimal.** Deleting a person is a true hard delete (GDPR right to erasure), never a soft "deactivated" flag. There are two erasure paths. (1) **An app user** (an HR operator's own account): remove every identity row (Better Auth `user`/`account`/`session`/`twoFactor`, all `member` rows, and any `invitation` addressed to any email the user has held, plus the `users` mirror) via `eraseUser` / `eraseSelf` / platform `deleteUser`. (2) **An employee** (a `people` row): `erasePersonAsOrg` hard-deletes the `people` row and its `payRecords` and `personAssignments`, child-first. Residual PII in append-only logs is anonymized, not retained: on erasure, replace the audit `actorName` snapshot AND its derived `searchText` with a tombstone (the name is denormalized into `searchText`, so tombstoning `actorName` alone is not enough), and keep the row for the trail's legitimate-interest basis. The future V2 frozen lönekartläggning snapshot (ADR-0011) is a scoped extension of this same anonymize-not-retain pattern: on erasure it pseudonymizes the individual within the immutable snapshot and keeps the aggregate (the statutory pay-mapping evidence document), rather than hard-deleting the frozen copy; the hard delete still applies to all live person data. Person PII (identity, salary) lives ONLY in the `people` bounded context (`people`, `payRecords`, `personAssignments`), the `users` mirror, the Better Auth tables, the frozen `payMappingSnapshotRows` (ADR-0011, the pay-mapping evidence document; pseudonymized on erasure, never hard-deleted), and the `person.*` audit diffs (ADR-0013: employee-identifying fields (display name, gender, birth date, employee number `externalRef`, job title) ARE diffed so a change to a person's record is traceable, and are tombstoned on erasure by `anonymizePersonAuditRows`, which rebuilds the derived `searchText` too); never add it to the `role`/`rating`/model/AI tables (Role ≠ Person). `payMappingRuns.collaboration` (samverkan participant names) is a scoped statutory exception to this allowlist with no erasure hook yet; see the go-live checklist entry in `docs/go-live-checklist.md` for the pre-launch decision. Every retained record that holds employee identity therefore carries its own erasure hook: identity is pseudonymized, never retained, and a new such record does not ship without its hook.

## In-app documentation

- **The user guide lives in MDX under `apps/dashboard/content/docs/<locale>/`** and is the assistant's only source of product knowledge beyond its system prompt (ADR-0019/ADR-0020). English is the source locale; every slug exists in every locale in `routing.locales`, and the slug is locale-invariant (only the content is translated), so a documentation path is never translated.
- **Any change under `content/docs/` ends with `bun run docs:sync` (from `apps/dashboard`), in the same change.** The corpus is chunked and embedded into the RAG component's index; until the sync runs, the assistant answers from the previous text AND the previous embeddings, which is a silent staleness with no test to catch it. The sync is incremental (a page whose content hash is unchanged costs no embedding call), so running it is cheap after the first time. The same applies to a chunker change: bump `CHUNKER_VERSION` (`lib/docs/chunk.ts`), which is part of the page hash and forces a full re-index.
- **The drift guards in `apps/dashboard/lib/docs/docs-guards.test.ts` are the corpus's contract** (locale parity, frontmatter, nav, internal links and anchors, error-code coverage, heading anchors). A new documentation rule ships as a guard there, not as a convention people are asked to remember.
- **After a chunker change, an embedding-model change, or any substantial corpus change, run `bun run docs:eval`** (from `apps/dashboard`) and compare recall against the numbers recorded in ADR-0020, instead of judging retrieval by eye. It is opt-in and costs embedding calls, so it is not in the test suite.

## Testing

- **All tests run with Vitest 4.** Never `bun test` (Bun hijacks it with its own runner; convex-test requires Vitest). Always `bun run test`.
- **Every package that has tests has its own `vitest.config.ts`** extending `@workspace/vitest-config` (`/base` or `/react`). No root vitest workspace/projects file; per-package configs are what let Turborepo cache test results per package.
- **New code ships with tests in the same commit.** The pre-commit hook runs the full `turbo run test`; the turbo cache keeps unchanged packages instant. Never use `--affected` in the hook (it misses staged changes).
- **Backend tests (`packages/backend`) use convex-test on the `edge-runtime` environment.** Full sign-in/session round-trips are e2e scope (Playwright, later), not unit scope.
- **Message files are parity-guarded:** the i18n test fails if any locale's key set differs from `en.json`.
- **shadcn vendor code (`packages/ui/src/*`) is untested by policy** (same rationale as its Biome exclusion).

## Conventions

- **Built for large organizations from day one.** Any write path whose work grows with org size (per-person or per-role writes: bulk confirms, imports, recomputes) runs as bounded chunks, never one unbounded mutation: either a client-driven chunk loop with visible progress, or scheduler-chained internal mutations (the import flow's pattern). A Convex transaction has hard document limits, and a long transaction invites OCC conflicts with everything else the org is doing. Size chunks by write cost, keep a natural unit (e.g. a title group) within one chunk when possible, and make partial completion honest and resumable (the UI reflects what landed; re-running finishes the rest). Org-scaled reads ride an index and stay bounded where the surface allows. Existing single-transaction org-scaled paths are tracked in `docs/go-live-checklist.md` for chunking before large-org onboarding.
- **No legacy before launch.** We are pre-launch: when something is replaced or retired, delete it completely in the same change (schema fields, tables, dead constants, compat shims, unused i18n keys) and reset dev/prod data instead of keeping retired columns around. Backwards-compatibility obligations start at go-live.
- **DRY and typed by default.** Never repeat the same literal, field list, shape, or logic across call sites: extract a shared constant, helper, or builder and use it everywhere (e.g. the audit field-list constants and `build*` helpers in `packages/backend/convex/lib/audit.ts`, the payload contracts in `lib/auditPayloads.ts`). Prefer a single source of truth that the type system enforces: type a payload/contract by the event or shape it belongs to (a typed map, discriminated union, or `keyof`-bound constant) so a wrong or missing field is a compile error, not a runtime surprise. Never widen to `any` to silence a type error or accept duplication "just for now". When you touch code that repeats itself or leans on untyped `Record<string, unknown>` envelopes, tighten it as part of the change.
- **Commit messages use conventional prefixes** (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`).
- **Leave completed work uncommitted for review.** Work directly in the main checkout's working tree and stop before committing: make the changes, then present them so the full diff can be reviewed first, and commit only after explicit approval. Do not create git worktrees or feature branches (they were tried and did not fit our flow). Once approved, commit as focused, single-concern commits on main.
- **Every finished task ends with a file-by-file change summary.** When presenting completed work for review, list every file created, modified, or deleted, each with a short note of what was done in it, grouped by area. The summary accompanies the report; never end a task with only a prose description of the outcome.
- **The pre-commit hook** (`.githooks/pre-commit`) runs Biome on staged files, a full typecheck, and the full test suite (`turbo run test`, cache-backed). All three must pass before a commit; never bypass with `--no-verify` unless explicitly told to.
- **Forms use react-hook-form + Zod + the shadcn `Form` components.** Every data-entry form uses `useForm({ resolver: zodResolver(schema), mode: "onTouched" })` and renders fields with `FormField`/`FormItem`/`FormLabel`/`FormControl`/`FormMessage` (`@workspace/ui/components/form`), so each field validates on blur and shows its error inline via `FormMessage`. Form schemas are **factories** `makeXSchema(t)` that build the Zod schema with translated messages (`t` is `useTranslations("dashboard.validation")`), so messages stay in i18n and `FormMessage` stays vendor-pure; shared messages live under `dashboard.validation.*`. The submit button is disabled until the form is valid (`disabled={!form.formState.isValid}`) and while submitting (`SubmitButton` + `form.formState.isSubmitting`, which combine the two); fields still surface their errors inline on touch. `isValid` updates live on every change in `onTouched` mode, so the gate is accurate without a blur. For a custom submit control (e.g. `NextButton`), pass `disabled={!form.formState.isValid || form.formState.isSubmitting}`. A type-to-confirm gate (e.g. delete-user) is the same idea: gate the action on `form.formState.isValid`. A **pre-filled edit/settings form** (valid the moment it opens) also gates on `form.formState.isDirty` (`disabled={!isValid || !isDirty}`) so an unchanged form cannot fire a no-op mutation (which would still write an audit row): e.g. the org-settings and edit-criterion forms. Create forms do not need `isDirty` (reaching `isValid` already requires filling the form), and wizard steps that must allow continuing unchanged (e.g. the onboarding name screen) never add it. The backend always re-validates independently (Convex validators + `appError` codes); Zod is the client's gate. Non-form payload schemas (the shape of stored or AI payloads, e.g. `apps/dashboard/lib/suggestion-schemas.ts`) stay plain Zod.
- **Lint + format = Biome** (`biome.json` at the root, a single binary). eslint/prettier are not in this repo; do not reintroduce them. **Biome ends every change at zero: no errors, no warnings, no info.** A warning is a defect, not a suggestion, so both gates run `--error-on-warnings` (the pre-commit hook and CI) and a warning fails the commit exactly like an error. Never leave one for later and never silence one with an ignore comment to get green; fix the code, or if the rule is genuinely wrong for this repo, turn it off in `biome.json` with a comment saying why. The `$schema` version in `biome.json` tracks the pinned CLI version, so a Biome upgrade runs `biome migrate --write` in the same change (a mismatch is itself a diagnostic). Unsafe fixes are applied deliberately by hand, never with a repo-wide `--write --unsafe`.
- **shadcn files are vendor code:** `packages/ui/src/{components,hooks,lib,styles}` are excluded from Biome and must not be reformatted or relinted. They must stay diffable against upstream and are updated via the shadcn CLI. Deliberate local fixes are fine but must be documented in the commit message.
- **Prefer shadcn defaults.** Use design-system components with their default variants, sizes, and tokens (heights, radius, shadows). Never hand-pick sizes or shadows per call site; deviate only when a component is explicitly meant to be custom, keep the override at the call site, and say why in a comment. **Always build UI from the `@workspace/ui` components (or the app primitives composed from them) when one exists; never fall back to a native control or hand-rolled markup for something the design system covers.** Dates are the canonical trap: a date field is the shadcn calendar picker (`DatePicker` / `DateRangePicker`, Button + Popover + `Calendar`), never `<input type="date">`; likewise selects are the `Select` component, never `<select>`. If a needed primitive is missing from `packages/ui`, add it via the shadcn CLI (vendor code) or compose an app primitive at the components root, and reuse it everywhere.
- **A file lives with the surface that owns it, never where it was born.** `apps/dashboard/components/` is organized by surface: `onboarding/` (the wizard frame and its step screens), `model/` (the model-editing surface including its AI panels), `roles/`, `rating/`, `levels/`. Reusable app primitives (the morph family) live at the components root; hooks in `hooks/`, pure helpers in `lib/`, shared test scaffolding in `test/`. The Convex backend stays organized by bounded context (`CONTEXT-MAP.md`). When a piece gains consumers outside its folder, move it to its owner surface in the same change; a hook must never import from a surface folder.
- **Guide the user through every concept.** Ease of use and guidance are the product's primary goal. Every surface that introduces a domain term (criterion, assessment anchor, level, anchor role) explains it inline in plain language, normally a `HelpMorphButton` with a `dashboard.help.*` key next to the term. Flows state their preconditions in words ("the role needs a completed assessment") instead of silently hiding or disabling controls. Never stack more than one help popover on the same heading or row; place each concept's help where the concept is used (a second concept's help goes next to its own control). A new domain concept ships with its help text, in all locales, in the same commit. **A help body is at most two sentences**: the first says what the thing is, the second exists only when there is one dominant mistake to prevent (in this domain, almost always the boundary against the neighbouring term: level vs seniority, weighting vs the 0-5 scale, role vs person). Nothing else belongs there, not rationale for its own sake, not a restatement of what the surface already shows. The cap is 200 characters in `en` and 240 in the other locales, which have room because Finnish runs ~7% longer; `messages.test.ts` fails a body over its cap and names it. Detail that a neighbouring help text already carries is not repeated, it is dropped.
- **Dialogs follow the standard shadcn anatomy.** `DialogContent` contains `DialogHeader` (`DialogTitle`, plus `DialogDescription` when there is copy), the body, and a `DialogFooter` with the actions right-aligned: cancel as an outline button first, the primary action last. Forms inside dialogs carry no panel chrome of their own (no border/padding box; the dialog is the panel) and their submit button lives in the footer.
- **Charts follow one anatomy.** **A chart inside a widget card draws on `ChartCanvas` (`components/chart-canvas.tsx`), which owns its height AND its type scale in both states.** Expanding a card is a request for a LARGER canvas, so the dialog sizes to the screen (capped, with a margin and a scrolling body) and the chart inside grows with it: `EXPANDED_CHART_HEIGHT` for the plot, `EXPANDED_CHART_TEXT` applied as a CLASS so every tick and in-plot label inherits it (a chart three times the size with 12px ticks beside it reads as a rendering mistake, not as a bigger chart), and `EXPANDED_POINT_MARK_SIZE` for point marks. It follows that **a chart in a widget card sets no `fontSize` on its axes**: an explicit prop beats inheritance and pins that one axis while everything around it grows; `CHART_AXIS_FONT_SIZE` is for charts outside a card, and it is the same 12px `ChartContainer` already inherits. Anything OUTSIDE the canvas that must grow with it (the legend, its swatches) reads `useWidgetExpanded()` itself. **Never call `useWidgetExpanded()` in the component that renders the `WidgetCard`**: it sits above the dialog's provider and silently answers `false`, so the chart keeps its card size inside the dialog and expanding gains width and no height. That bug shipped once and is invisible in review, because the code reads correctly and only the value is wrong; the decision lives in a child component for exactly that reason, and `chart-canvas.test.tsx` pins it. Every chart's geometry and hover come from `apps/dashboard/lib/chart-style.ts`, never a per-call-site literal: `CHART_TOOLTIP_TEXT` (hover type size), `CHART_AXIS_FONT_SIZE` (axis ticks; never shrink a chart's own ticks below it), `BAR_RADIUS` (bar corners), `WIDGET_CHART_HEIGHT` (the assistant's chart parts' plot strip, shared with their loading placeholders so the two can never drift). **Every chart hover renders at `CHART_TOOLTIP_TEXT`**, including hand-built tooltip content: shadcn's `ChartTooltipContent` ships at `text-xs`, so a chart that takes the default reads visibly smaller than the cards beside it and than its own legend (guarded by a test in `components/gender-mark.test.tsx`). A chart's legend is `GenderLegend`-style markup outside the plot, not recharts' `ChartLegend`, and it shares its row component with the tooltip so the two always match; matching the vendor row's classes from outside does not work, because it carries `leading-none` on an inner element no override reaches. Bars that bleed to a card's clipped bottom edge round their top corners only. **Every patterned mark carries a border in ITS OWN series' ink, with no exceptions**: SVG chart marks via `genderMarkBorder(series)`, HTML marks (CSS bars, legend and tooltip swatches) via the border baked into `genderFillStyle`/`genderKeyStyle`, and the SVG key via `GenderMenIcon`. `genderMarkBorder` takes a required series argument rather than being one constant, because while both series shared one ink every call site spread the same object onto both bars, and with two hues that outlines the women's bar in the men's blue. The SOLID series edges in `--gender-woman-edge`, a darker step of its own ink, not the ink itself: a hatch is a pale wash so the ink already contours it, while a solid fill outlined in its own colour has no visible edge, which left the two series looking differently CONSTRUCTED rather than differently filled. **A new `--gender-*` token must also be registered in `@theme inline` (`--color-<name>: var(--<name>)`) or the build strips it** and it silently resolves to nothing; a test asserts the registration. A new surface that draws the hatch draws the border with it. The reason: a hatch is stripes with no edge of its own, so an unbordered hatched shape reads as a smudge fading into the card instead of a bounded area, and the border doubles as the separator between stacked segments. An area chart's fills stay light under a visible stroke (the stroke is what makes a series read as a curve); two saturated stacked bands flatten into blocks. **Gender is encoded REDUNDANTLY, by hue AND by mark** (see `components/gender-mark.tsx` and the `--gender-*` tokens): hue is the fast channel, the mark is the one that survives greyscale, print, and a reader who cannot separate the two hues. Never encode gender with colour alone. The pair is a terracotta orange (women) and a denim blue (men), because the blue-yellow opposition is the only one that holds under all three dichromacies; cool/cool pairs measured well on screen and then collapsed into a single colour under simulated deuteranopia (verified by rendering the real charts through an `feColorMatrix` simulation, not by eye). Neither is the brand rose, so a chart never competes with the CTA and title colour beside it, and neither is pink, which no pay-equity chart should put on "women". Both inks clear 3:1 against the card in both planes, which is a real constraint rather than a nicety: the familiar soft blue of this category measures 2.96, and the men's series is drawn hatched on top of whatever contrast it starts with. `gender-mark.test.tsx` reads `globals.css` directly and fails if the two tokens ever converge or land back on `--brand`: nothing in the component layer can catch that, since every mark references the tokens and would keep passing while rendering one ink. Which mark depends on the family. **Area marks** (bars, bands, arcs) use fill texture: women solid, men hatched. **Point marks** (every scatter and dot plot) use SHAPE: **women a triangle, men a square**, app-wide and never varied per chart, both solid. **Neither is a circle, and that is load-bearing**: the circle is the app's UNGENDERED point, drawn by a plot that encodes something else on the same marks (the role mode below), and a gender owning that shape would keep its points reading as that gender on a chart where gender is not encoded at all. Shape as well as hue, because two overlapping marks differing only in fill cannot be counted and a dot plot's whole job is showing where individuals sit; a hatch cannot do it either, since the pattern tile is wider than the mark. The two shapes carry equal weight because recharts draws symbols through d3-shape, where `size` is AREA. **A point mark fills with `transparent`, never `none`**: they look identical but SVG hit-testing follows the paint, so `fill="none"` leaves a ring's interior untargetable and the hover answers only on the stroke. **A chart's legend and hover show its own family's mark**: `GenderLegend`/`GenderKeyRow` take `mark="point"` for a scatter (rendering `GenderDotIcon`) and default to the hatched square for area charts. A legend showing a hatched square beside a plot of hollow rings is a defect, not a variation. **A trend of these series is ONE series of the total, never stacked and never one per gender**: two gender lines sit ~20 apart while each moves by 1-2, which no single axis can both fit and magnify, and stacking them draws a comparison the reader cannot actually make. The single total is sized to its own movement (`trendDomain`, shared by the headcount and pay-gap trends) and the split moves to the hover, which costs nothing and leaves the mark free of the encoding. That one series draws as a gradient-filled area rather than a bare line, and the fill is texture rather than a magnitude claim: it is only safe BECAUSE there is one band with nothing to compare its height against, since a realistic headcount change (118 to 121) on the zero-based axis an honest magnitude would demand is about one pixel. A second band would have to sit on zero. Stripe weight is not one value: a 10px key needs heavier stripes than a full-size bar, so `genderKeyStyle` and `genderFillStyle` are separate calls. **A chart may switch WHICH ENCODING its marks carry, but only by taking the previous one off the surface completely.** The equivalent-work scatter's role toggle is the case: in role mode a point's HUE answers "which job is this" (`lib/role-palette.ts` over the `--role-*` tokens), gender is not encoded at all, and the gender key comes off the legend with it, because a key naming a distinction the plot no longer draws is worse than no key. **Shape is NOT a categorical channel here.** It was tried and taken out: at mark size a shape difference is a few pixels of silhouette, it cannot carry six categories, and hue plus shape made a plot of individuals read as a plot of symbols. Shape stays where it is load-bearing, on gender, which has two categories and has to survive greyscale and print. What keeps a six-hue plot off colour alone is not a second channel on the mark but the surface around it: the legend names every hue, the hover names the point's own job, and clicking a key puts every other job away, so a reader who cannot separate two hues can still isolate either one. The hues are Okabe-Ito (Wong 2011) minus its black and its yellow, which measures 1.32:1 against white; the canonical six, unaltered, because re-stepping them to lift the two faint steps to 3:1 walks the sky blue toward the reddish purple and costs more separation than it buys. Measured with `--pairs all` they land in the method's FLOOR band (CVD ΔE 7.6, normal vision 15.6), not over its target, and two steps sit under 3:1 against white. Both are conditional relaxes that this surface genuinely satisfies: the legend names every job and filters the plot, the hover names the point's own job, and the comparator table above is the table view of the same rows. A surface that offers none of those may not use a floor-band palette. Six slots, assigned in the order the surface already lists the jobs (never re-ranked, or a filter repaints the survivors) and never cycled: a seventh job folds into `--role-other`, because a repeated hue says "the same job". The hues were run through the dataviz validator against both surfaces, not picked by eye; `lib/role-palette.test.ts` reads `globals.css` for the same reason the gender test does. Mark GEOMETRY lives in `components/point-mark.tsx` (`PointMark` for the plot, `PointShapeIcon` at key size), which the gender marks are built from too, so the two families can never drift into different weights for one size. Every surface follows the plot: the key shows each job's own shape, the hover moves its mark onto the line that mark names, and no mark ever appears without something naming it. **Every chart key is built from `components/chart-legend.tsx`** (`ChartKeyRow` + `ChartLegend`), so a gender key and a role key can never drift into different pitches: the gender and role families supply only which MARK a series wears. A key of two or three fixed series (especially one carrying a figure per row) runs down in the `column` layout; a key as long as the data is runs across, centred under its plot, because six jobs stacked vertically push the chart's own findings off screen. **A key that names more than a couple of series is also a FILTER**: each row is a real toggle button (`aria-pressed`, keyboard-reachable, dimmed when off and never removed, so the way back is where it was), a hidden series takes its own derived marks with it (an average line for people who are not on the plot is a number with nothing to read it against), and the last key that actually DRAWS something cannot be switched off, because an empty plot has nothing left on it to click back.
- **Tables follow one anatomy.** A register table (people, roles) is a TanStack data table: a toolbar with search + select filters (a result count appears while narrowing), sortable headings, and client pagination (`TablePagination`) past 25 rows. Every sortable table declares a default sort (people: name ascending; classify: title ascending). Sortable headings are plain heading text rendered via `TableSortButton` (hover underline, an up/down chevron only on the actively sorted column, inside a pre-reserved slot so nothing shifts) in a `TableHead` carrying `aria-sort`; the first click sorts ascending, the second flips to descending, and a sort change resets to page 1. Every data table is `table-fixed` with column widths declared once on the header cells (one flexible column takes the rest; flexible text cells `truncate`), so widths never re-measure from content on page flips, filtering, or the skeleton swap. Grouped registers (roles by family) and chronological histories (salary, audit log) take no per-column sorting: the grouping or the timeline is their order.
- **Row and table actions use a dropdown menu, not inline buttons.** Per-row actions live behind a single trailing `...` trigger (a ghost icon `Button` with `MoreVerticalIcon` and an aria-label) that opens a `DropdownMenu` of `DropdownMenuItem`s; a destructive item uses `variant="destructive"` and opens an `AlertDialog` to confirm. This keeps rows uncluttered and consistent (see `components/model/criterion-item.tsx`). A section's standalone primary action (e.g. a "Create" button above the table) stays a button.
- **Minimize layout shift in the UI.** State changes (hover, edit modes, inline confirms, loading) must not reflow existing content: reveal controls with opacity or overlays inside pre-reserved, fixed-size slots; never insert or remove inline elements that resize their neighbors. New content may extend below existing content, but what is already on screen stays put.
- **A page or section that loads data shows a content-shaped skeleton.** When a surface is waiting on its own data (a Convex `useQuery` returning `undefined`), render a skeleton that mirrors the real content in the same layout, instead of holding a blank screen or a centered spinner, so the structure appears instantly and nothing reflows when the data arrives (this is how a data load satisfies "minimize layout shift"). Tables render `TableSkeleton` in place of `<TableBody>` inside the same `<Table>`; the model criteria list renders `CriterionListSkeleton` shaped per phase (`define`/`weight`/`method`), including the phase's toolbar placeholder. A new data-backed surface ships its skeleton in the same change. This is not a blanket preference for skeletons over spinners: a `Spinner` is still the right choice for in-place action feedback, such as a button mid-submit or an inline control, where there is no content shape to stand in for. **Skeleton rows must MEASURE identical to data rows**, not just look similar: `TableSkeleton` centers each bar in a text-line box for this, and inline-flex controls (`Badge`, `Button`, a `...` menu trigger) inside a table cell must sit in a block flex wrapper (`<div className="flex items-center">`), never directly in the cell, because on the text baseline they inflate the line box by a font-metric-dependent amount that desyncs the two states (found by measuring rendered rows in headless Chrome, not by eye). Skeleton bars stand in for unknown DATA only: per-row chrome that is identical for every row (an expand chevron, a row-actions trigger) renders as its real icon, muted and non-interactive, via `TableSkeletonColumn.content` instead of a gray bar. The same rule governs page chrome: a control whose label is static i18n text (a toolbar search input, a filter select, a primary action or menu-trigger button, a tab bar) renders as its REAL component while the data loads, never as a gray bar, and normally enabled rather than disabled: the load is brief, interacting with a not-yet-wired control is a harmless no-op, and a disabled control would flash gray on arrival. Prefer sharing the live control between the loading and loaded branches when its state lives outside the data (the people toolbar: a search typed during loading carries over); a filter whose options are still loading renders showing its all-option. Use disabled only when the loaded control's initial state is itself disabled (the rating stepper's nav buttons). Bars are only for content that is unknown until the data arrives (a data-driven title, a count, per-row values, a state-dependent CTA label). A paginated table's skeleton shows a full page of rows: `rows` is the same `PAGE_SIZE` constant the pager uses (one shared constant, never a second literal), so the table does not grow when the first page arrives. Unpaginated tables size their skeleton to the typical content instead.
- **User-initiated CRUD shows a toast.** Every create / update / save / delete / remove / archive / approve a user triggers confirms completion with `toast.success(t("dashboard.toast.<op>"))`, so nothing completes silently. The `toast` object comes from `@/lib/toast`, the app's two-method API (`success`/`error`) over the Base UI toast manager in `@workspace/ui/components/toast`; its host `<Toaster>` is mounted app-wide in `providers.tsx`, and because the manager is a module singleton a call reaches it from anywhere. Call sites never call the manager's `add` directly: the status `type` and the announcement `priority` are mapped once in `lib/toast.ts` (errors are announced urgently), so a new status or option is added there rather than at each of the ~170 call sites. On failure show `toast.error(t("dashboard.toast.error"))` where the surface has no other error affordance; keep inline `FormMessage` field validation for form errors. Toast copy lives in `dashboard.toast.*`, per-operation and localized in every locale. Not everything toasts: multi-step wizard/onboarding steps (navigation is the feedback), AI generation requests (their panel shows the result), and continuous/auto-saves such as per-criterion rating (a toast per step is noise). A new CRUD surface wires its toast in the same change.
- **Animate legitimate transitions.** We favor animation to make the UI feel alive: when content genuinely enters or leaves (list items added/removed, state morphs), animate the change instead of letting it jump. The dashboard uses Motion (`motion/react`): `AnimatePresence` + `layout` for lists, layout springs for morphs. Reduced motion is respected globally via `MotionConfig reducedMotion="user"`; never bypass it. **Read `docs/ui-animation.md` before writing or reviewing any animation**; it records the bugs we already shipped once (FLIP scale distortion, height-vs-box-model clamping, gap collapse, overflow vs corner overlaps).
- **Live numbers render through NumberFlow.** A standalone numeric value that changes while it is on screen (a header tab's notification count, a running progress readout) renders with `@number-flow/react` so updates roll digit-by-digit instead of swapping. Nav tab counts go through the shared `NavCountBadge` (`apps/dashboard/components/nav-count-badge.tsx`: brand Badge + NumberFlow + spring enter/exit, hidden at zero); other live numbers use `NumberFlow` directly. NumberFlow respects reduced motion by default; never turn that off. i18n boundary: a number embedded in a translated sentence stays plain text (never split an ICU message around a component to force the animation); when a message is purely numeric layout (e.g. "{done} / {total}"), convert it to a tag-based rich message (`<done></done> / <total></total>` rendered with `t.rich`) so the numbers carry NumberFlow without leaving i18n. One-shot values that mount once and never change on screen (a revealed score, ordinary table cells) stay plain text.
- PDFs are built with `./docs/build-pdf.sh` (pandoc + typst), never Chrome headless.
- Next.js 16: `proxy.ts` (not `middleware.ts`); the proxy must export an explicit function.
- **Route-exposed entities use a slug, never a raw id, in the URL.** Every entity reachable by its own route carries a required `slug` (lowercase, hyphenated, ASCII-folded via `@workspace/constants` `slugify`), generated from its display name at creation and regenerated on rename, unique per org via a `by_org_slug` index; when the name has no slug-able characters, fall back to a short id (`crypto.randomUUID()` slice). Generate it with the shared `uniqueSlug` helper (`convex/lib/slug.ts`). Routes resolve by `(orgId, slug)` from the caller's active org (so the same link maps to each viewer's own org), and the Convex `_id` stays the permanent internal key that mutations take. Today this governs `roles` (slug from `title`) and `roleFamilies` (slug from `name`). `people` are the PII exception: never a name-derived slug (PII in URLs) and never the raw id; they carry a short random `publicId` (`uniquePersonPublicId` in `convex/lib/slug.ts`, resolved via `by_org_publicId`) under the same resolution rule.
