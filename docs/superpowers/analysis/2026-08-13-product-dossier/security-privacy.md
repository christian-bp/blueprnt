# Security and privacy dossier

## Behavior today

**Data residency.** blueprnt runs on managed Convex Cloud in the EU (AWS eu-west-1, Ireland) and uses Better Auth (organization plugin, Local Install component) for auth and multitenancy inside the same Convex deployment (ADR-0001, `docs/adr/0001-convex-eu-better-auth.md`). Transactional email goes through Sweego (`@christian-ek/sweego` component), which must meet the same EU-hosting requirement; confirming Sweego's hosting region and signing a DPA is still an open go-live item (`docs/go-live-checklist.md`). The web tier (`apps/dashboard`, Next.js on Vercel) is pinned to the `dub1` (Dublin) region via `apps/dashboard/vercel.json`, verified in code.

**Auth and session hardening.** `packages/backend/convex/auth.ts` configures Better Auth with sign-in rate limiting, explicit session lifetime (`session.expiresIn`/`updateAge`), and explicit cookie attributes (`sameSite`, `secure`, `httpOnly`, a cookie prefix, `trustedOrigins`), per `docs/superpowers/specs/2026-06-26-cra-hardening-design.md`. The dashboard app ships security response headers (`Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`) and a `Content-Security-Policy-Report-Only` header, confirmed present in `apps/dashboard/next.config.ts`. A vulnerability-disclosure channel exists as `SECURITY.md` (repo root) and `apps/dashboard/public/.well-known/security.txt` (RFC 9116), both confirmed present in the repo. CI (`.github/workflows/ci.yml`, `osv-scanner-*.yml`, `sbom.yml`, `secret-scan.yml`) mirrors the pre-commit gates and adds OSV-Scanner CVE scanning, a secret scan, and SBOM generation.

**Mandatory two-factor authentication.** Every user must confirm a second factor before reaching the dashboard: a `TwoFactorGate` sits in `apps/dashboard/app/(app)/layout.tsx` before `OnboardingGate` (design: `docs/superpowers/specs/2026-06-26-mandatory-2fa-design.md`; backend confirmed at `packages/backend/convex/accounts/twoFactor.ts`). Two methods: authenticator app (TOTP) or email codes (OTP); email is also the universal recovery fallback. The app's own "setup complete" signal is `mfaConfirmedAt` on the `users` mirror row (not Better Auth's `twoFactorEnabled`, which flips true at `enable()` before the method is actually confirmed, because `skipVerificationOnEnable: true`). `getMyMfaStatus` (a plain `query`, not `authedQuery`, deliberately, so an auth-token refresh blip returns `null` instead of throwing and unmounting the gate) returns `{ confirmed, method }`. `confirmMfaSetup` (`accounts/twoFactor.ts`) independently re-checks with Better Auth's `hasTwoFactorEnabled` before stamping `mfaMethod`/`mfaConfirmedAt`, so a client cannot self-report completion without having actually passed the password-gated `enable()` step. No 2FA-disable path exists; 2FA is mandatory and, per the design, cannot be turned off in V1. There is no exemption for any account, including the two seeded founder accounts (`docs/go-live-checklist.md`: "There is no 2FA exemption... these accounts use real email 2FA like everyone else").

**Platform administration (a deliberate cross-tenant exception).** Every ordinary Convex function is org-scoped through `orgQuery`/`orgMutation`/`adminMutation` (`packages/backend/convex/lib/functions.ts`), which resolve the caller's membership via `resolveOrgContext` and deny by default. Platform administration is the one exception (ADR-0009, `docs/adr/0009-platform-admin.md`): a boolean `isPlatformAdmin` flag on the `users` mirror, set only out-of-band (Convex CLI/dashboard via `internal.platform.bootstrap.grantPlatformAdminByEmail`/`revokePlatformAdminByEmail`, or the dev/pre-launch seed). `platformQuery`/`platformMutation` (`lib/functions.ts`) take no `orgId` argument at all (confirmed: the absence of the argument is the structural guard) and call `requirePlatformAdmin`, which throws `errors.platformAdminRequired` when the flag is not `true`. Frontend gating (hiding the admin link, showing a not-authorized page) is cosmetic; the builder is the real boundary. The `/admin` route (`apps/dashboard/app/(app)/admin/`) has sub-pages for audit log, email log, organizations, and AI usage, all confirmed present in the repo.

**Separate platform audit log.** Every platform-admin action writes exactly one row to a separate `platformAuditLog` table via `logPlatformAudit` (own `PLATFORM_AUDIT_EVENTS` vocabulary), never to any tenant's own `auditLog`. The one exception is `organization.created`, written by `onOrganizationCreate` with actor `"system"` when a platform admin creates an org, which is the org's own intrinsic lifecycle row. `platformAuditLog` categories, confirmed in `lib/audit.ts` as `PLATFORM_AUDIT_CATEGORIES`: `user`, `organization`, `membership`, `admin`. The platform log's UI (`apps/dashboard/components/admin/audit-log-section.tsx`) mirrors the org audit log's toolbar (category filter, search, pagination) and detail sheet, sharing pure helpers (`lib/audit-detail.ts`) and a `ChangeEntryRow` component with the org log (`docs/superpowers/specs/2026-06-20-admin-audit-log-parity.md`). The platform log's `searchText` is built only from `actorName + type + payload scalars`, never from a resolved target's email or name, because the platform log's invariant is id-only payloads with no PII, so erasure must leave nothing to scrub.

**Org audit log.** Every state-changing mutation writes one row via `logAudit` (`packages/backend/convex/lib/audit.ts`) carrying `orgId`, `type`, `actorId`, a snapshotted `actorName`, a `category` (derived via `categoryForEvent`), a `searchText`, and a typed `payload`. Confirmed categories in code (`AUDIT_CATEGORIES`): `model`, `role`, `organization`, `member`, `ai`, `people`, `pay`. The payload is a discriminated union per event, typed in `lib/auditPayloads.ts` (`AuditPayloads`), so a wrong or missing field is a compile error. Every payload field resolves to a `dashboard.auditLog.fields.*` label in every locale (guarded by `audit-labels.test.ts`); coded/enum values (scope, verdict, area code, reason code) resolve through `resolveCodedValue` rather than showing the raw wire string. A `changes` map (before/after) renders as an arrow diff; a flat-stats payload (no `changes` map) renders through `payloadStats`/`StatList`. The audit log's pager gets its exact total/offset from two `@convex-dev/aggregate` instances maintained inside `logAudit` (`lib/auditAggregates.ts`), storing only namespaces and `_creationTime` keys, no PII.

**Person identity in the audit trail (ADR-0013).** Every person data field, including identity fields (`displayName`, `gender`, `externalRef`, `birthDate`, `title`), is diffed in the audit log (`PERSON_AUDIT_FIELDS`). This reversed an earlier invariant that excluded identity fields, because excluding them produced empty, useless rows for the most common edits (fixing a name, an employee number, a gender). On erasure, `anonymizePersonAuditRows` (`lib/audit.ts`) replaces every `PERSON_IDENTITY_AUDIT_FIELDS` value with the tombstone constant `ERASED_FIELD_VALUE` and rebuilds the derived `searchText` for every row about that person; the row itself and its structural fields (department, country, FTE, employment type, manager flag) survive. The `person` audit subject (`{ kind: "person", id }`) exists so this scrub can find a person's rows via `by_org_subject` without scanning the whole org trail; no product surface reads the subject for browsing today (ADR-0013 says the `person` subject exists for erasure, not for browsing).

**GDPR erasure paths, three of them.**
1. **A person (`people` row), HR-initiated.** `erasePersonAsOrg` (`packages/backend/convex/people/erase.ts`), an `adminMutation`, hard-deletes `payRecords`, then `personAssignments`, then the `people` row itself, child-first, then pseudonymizes the person inside the frozen pay-mapping snapshot (`pseudonymizePersonInSnapshots`, ADR-0011) and inside the audit trail (`anonymizePersonAuditRows`, ADR-0013). This is a true hard delete, never a soft "deactivated" flag. The audit row written at erasure time uses `PERSON_ERASURE_AUDIT_FIELDS` (`PERSON_AUDIT_FIELDS` minus the identity fields) so the erasure mutation itself can never re-introduce the values it is simultaneously scrubbing from earlier rows.
2. **A user erasing their own account.** `accounts/account.ts` `deleteMyAccount` -> `eraseSelf`: hard-deletes Better Auth `user`/`account`/`session`/`twoFactor` rows, all `member` rows, the `users` mirror, the person's Sweego email history (`email/erasure.purgeRecipientEmails`, keyed on the current Better Auth address so it runs even if the app mirror is missing), and their assistant chat threads/messages across all orgs (ADR-0018), then anonymizes their `actorName` (and derived `searchText`) in both audit logs. Blocked if the caller is the sole admin of any org (`errors.lastAdmin`); requires password re-authentication (e2e-only coverage, per the go-live checklist).
3. **A platform admin deleting another user.** `platform/admin.ts` `deleteUser`, a `platformMutation`, does the identical identity-row hard delete plus the same Sweego/assistant/audit-anonymization steps, but writes only to `platformAuditLog` (never the org log), with a payload carrying a non-identifying `orgCount`, never the erased person's name or email. Self-delete is blocked (`authId === ctx.authUserId` throws `errors.invalidInput`).

**AI usage tracking.** Every AI generation call (`convex/ai/generate.ts`) records one immutable `aiUsageEvents` row plus a patched `aiUsageMonthly` per-org-per-month rollup, via `internal.ai.usage.recordAiUsage` (design: `docs/superpowers/specs/2026-06-10-ai-usage-tracking-design.md`). Fields: `orgId`, `kind`, `provider`, `model`, `inputTokens`/`outputTokens`/`totalTokens`/`cachedInputTokens`, `estimatedCostNanos` (integer nano-USD, computed from a `MODEL_PRICING` constant and frozen at write time so later price changes never rewrite history), `actorId` (from the suggestion's `requestedBy`), `suggestionId`. This is observe-only telemetry: it records what AI calls cost, enforces no quota, and does not write an `AUDIT_EVENTS` row (a documented carve-out: the audit invariant governs user-initiated domain changes, and an append-only telemetry log is itself the record). A platform-admin-only page at `/admin/ai-usage` (plan: `docs/superpowers/plans/2026-08-13-admin-ai-usage.md`) shows KPI tiles, a ranked-bar chart of cost by org with outlier flagging (cost above 3x the cross-org median, or an absolute floor), and a per-org table, reading `convex/platform/aiUsage.ts`.

**AI input-side PII screen.** Before an assistant generation reaches the model, `containsEmployeeName` (`convex/assistant/insights.ts`, an `internalQuery`) checks the caller's message against every employee's full display name in the org; a match fails the generation with `errors.assistantPersonalData` rather than sending the message to the model (ADR-0018). This check collects every person in the org via `by_org` per assistant message, an org-headcount-scaled read the go-live checklist flags for bounding before large-org onboarding.

## Terms and history

- **Tenant / Organization.** A Better Auth organization is the tenant (code: `Organization`; glossary: `docs/contexts/accounts/CONTEXT.md`). Every ordinary Convex function is scoped to exactly one `orgId`; there is no cross-org data access except through the platform-admin exception. Avoid: Arbetsyta/Workspace, retired 2026-06-05 (`organization.md` line 29, `glossary.md` line 92, both citing `docs/contexts/accounts/CONTEXT.md`); it is not the current glossary term, it is the term the glossary explicitly retired in favor of Organization.
- **Platform administrator** (ADR-0009): an operator role identified by `isPlatformAdmin`, entirely outside the org-role system (`admin`/`editor`). Not to be confused with an org `admin`, who is scoped to one organization.
- **Audit log vs platform audit log.** "Audit log" (`auditLog`, Swedish: revisionslogg/Händelselogg) is per-organization and records domain changes. "Platform audit log" (`platformAuditLog`) is the separate, org-free operator trail for cross-tenant provisioning actions. They deliberately never mix: a tenant admin never sees the platform operator's actions in their own log.
- **Anonymize, not retain (the recurring pattern).** The same pattern appears in three places: (1) a deleted user's `actorName`/`searchText` in both audit logs, tombstoned to the constant `ERASED_ACTOR_NAME` ("deleted user"); (2) a person's identity fields in their `person.*` audit diffs, tombstoned to `ERASED_FIELD_VALUE` (ADR-0013); (3) an individual pseudonymized inside the frozen pay-mapping snapshot while the aggregate (the statutory evidence document) is kept (ADR-0011). None of these are anonymous in the strict sense; they are pseudonymized residuals kept on a legitimate-interest legal basis (ADR-0013 is explicit that the correct claim is "no direct identifiers survive erasure," not "no personal data remains").
- **Role != Person** (also a glossary boundary term): the `role`/`rating`/model/AI tables must never carry person, salary, or performance fields. This is unaffected by ADR-0013, which governs only `person.*` audit diffs.
- No ADR-0014 terminology (Level/Seniority/Step) content applies to this section; none of the reviewed security-privacy sources used the pre-ADR-0014 vocabulary (Band/Nivå/anchor-scale level), so no translation was needed here.

## Rationale

- **EU residency choice and its limits.** ADR-0001 chose managed Convex EU (eu-west-1) over self-hosting or a US-hosted alternative because it keeps zero-ops benefits while satisfying "physically in the EU," which was confirmed as sufficient for V1; strict EU sovereignty was explicitly deferred until a customer contractually requires it. eu-west-1 is an AWS region under a US parent company, so this is GDPR residency, not sovereign-cloud independence (ADR-0001).
- **Region choice is a one-way door.** ADR-0001/design spec: Convex deployments cannot be migrated between regions; a region change requires backup and restore. The region must be set before any project is provisioned.
- **Platform admin is a documented, narrow exception.** ADR-0009's stated reason for building `platformQuery`/`platformMutation` at all: provisioning tenants and users has to happen before any customer can sign in, and no existing org-scoped capability can do that without contradicting tenant isolation. The absence of an `orgId` argument is chosen specifically as a structural (compiler-visible) guard, not just a runtime check.
- **Separate platform audit log, not a shared one.** ADR-0009's rationale: operator actions must never appear in a tenant's own audit trail, and the platform log must be the sole, unmixed record of operator activity, so tenants and operators each get an authoritative, uncontaminated trail.
- **Why identity fields were added back into person audit diffs (ADR-0013).** The prior exclusion of identity fields from `PERSON_AUDIT_FIELDS` was meant to keep the append-only log PII-free by never writing PII into it, but it made the most common edits (fixing a name, correcting an employee number) produce empty `changes: {}` rows, i.e. the log proved something happened but not what. ADR-0013 chose "diff everything, then pseudonymize on erasure" over "never diff identity," because a revision trail that can't show what changed has no audit value. It explicitly states this is a correction, not the same tradeoff loosened: erasure remains a genuine hard delete of live data, and no direct identifier survives it.
- **Mandatory 2FA re-authentication before enabling (mandatory-2fa design, section 7).** Enrolling or replacing a second factor is treated as a high-risk action per OWASP MFA/NIST SP 800-63B, so the setup flow re-confirms the user's password at the `enable()` step rather than trusting the live session (which could be hijacked). No plaintext password is retained in client state across steps.
- **Why AI usage tracking is observe-only telemetry, not an audited domain mutation.** The design (`2026-06-10-ai-usage-tracking-design.md`) argues the audit invariant governs user-initiated changes to auditable domain state, and `aiUsageEvents` is itself an append-only record, so writing a duplicate `AUDIT_EVENTS` row would be redundant. This carve-out needed ratification into CLAUDE.md's wording (done: CLAUDE.md's audit-log section now states the scope explicitly).
- **Why the AI input screen scans for employee names before generation (ADR-0018 per the assistant spec).** The strict no-individual-PII posture for AI (never sending a name/salary/performance detail to the model) is enforced structurally at the input boundary, not left to prompt discipline, because the assistant is a chat surface where a user could type anything.
- **Why cost is frozen at write time, not recomputed later.** The AI usage design explicitly rejects deriving historical cost from a current price, because model pricing moves and that would misattribute cost retroactively.

## Edge cases and error states

- **`errors.notAuthenticated`** ("You need to sign in.") — thrown by `orgQuery`/`orgMutation`/`platformQuery`/etc. (`lib/functions.ts`) whenever `ctx.auth.getUserIdentity()` returns `null` for a function that requires it. Fix: sign in again; a stale/expired session needs a fresh sign-in.
- **`errors.notAMember`** ("You are not a member of this organization.") — thrown when the caller is authenticated but has no membership row for the requested `orgId` (`lib/functions.ts`). Fix: switch to an organization you belong to, or ask an org admin to add you.
- **`errors.adminRequired`** ("Only organization admins can do this.") — thrown by `adminMutation` when the caller's org role is not `admin` (e.g. an `editor` calling an admin-only mutation). Fix: ask an org admin to perform the action.
- **`errors.platformAdminRequired`** ("You do not have platform admin access.") — thrown by `requirePlatformAdmin` inside every `platformQuery`/`platformMutation` when the caller's `users` mirror row does not have `isPlatformAdmin === true`. This flag can only be granted out-of-band (Convex CLI/dashboard); there is no in-app request or self-service path. Fix: contact a platform operator; there is nothing an end user can do in-app.
- **`errors.membershipConflict`** ("Your membership could not be verified. Contact support.") — thrown when the membership resolution finds an inconsistent/ambiguous state (`lib/functions.ts`). Fix: contact support; this indicates a data inconsistency, not a normal permission gap.
- **`errors.lastAdmin`** ("You're the last administrator of an organization. Contact support to delete your account.") — thrown by `deleteMyAccount`/`eraseSelf` (and by `updateMemberRole`/`removeMember` in `accounts/organization.ts`) when the action would leave an org with zero admins. Fix: promote another member to admin first, or contact support for account deletion.
- **`errors.invalidInput`** — reused generically; in the platform-admin surface it also covers self-delete rejection (`deleteUser` throws it when `authId === ctx.authUserId`) and a `confirmMfaSetup` call where Better Auth does not actually show 2FA enabled for the caller (defends against a client trying to self-report 2FA completion without having passed `enable()`).
- **2FA gate states:** `getMyMfaStatus` returns `null` (not an error) during a brief auth-token refresh blip, deliberately, so the reactive gate does not unmount and lose wizard progress; a genuinely signed-out caller cannot reach the gate at all. A user who enables 2FA in Better Auth but abandons before confirming a code has `twoFactorEnabled: true` upstream but `mfaConfirmedAt` still null in the app's own state, so the gate correctly keeps re-showing setup (they remain protected; email is always available as the completion path).
- **`errors.assistantPersonalData`** ("The message seems to include an employee's personal details. Remove them and ask again in general terms.") — thrown by the assistant generation path (`assistant/generate.ts`) when `containsEmployeeName` matches a full employee display name in the caller's message before it would otherwise reach the model. This is the AI-boundary PII gate in this section's scope (assistant-specific errors like `assistantBusy`/`assistantRateLimited`/`assistantInvalidMessage` belong to the assistant section, not privacy).
- **No admin-page self-authorization loop:** the avatar-menu admin link and the not-authorized page shown to a non-platform-admin are purely cosmetic; hiding the link is not the security boundary, so a determined non-admin who navigates to `/admin` directly still gets rejected server-side.
- **Erasure has an atomicity edge case (documented, unresolved as a go-live gap):** `erasePersonRecords` runs as a single transaction; the go-live checklist flags that an org with heavy per-person audit history (e.g. many nightly-sync `person.updated` rows) could hit Convex's per-transaction limits, which would make erasure for that person permanently fail rather than partially leak PII (the mutation is atomic, so failure is total, not partial). The recommended fix, not yet implemented, is to invert the order (scrub the trail in bounded chunks first, delete the `people` row last) when this is chunked.
- **Re-erasure / re-import is an open question, not a solved one:** nothing records that an `externalRef` has been erased, so a later payroll import containing the same employee number silently re-creates the person with full identity and a fresh identity-bearing `person.created` audit row. This predates ADR-0013 but now also re-introduces identity into the trail. Flagged in the go-live checklist as an undecided policy choice (a suppression list vs. an explicit "this is a controller process" statement).

## Deliberately absent

- **In-app granting or revoking of platform-admin status.** ADR-0009 and the platform-admin design both state this is out-of-band only (Convex CLI/dashboard) for V1; there is no UI for it.
- **Soft-deactivation of a user or a person.** Every erasure path in this section is a true hard delete; there is no "deactivated" flag anywhere in these flows (ADR-0009, ADR-0013, people/erase.ts).
- **A backup-code sheet for 2FA.** The mandatory-2FA design explicitly has no separate backup-code UI in V1; email codes are the sole recovery fallback for authenticator users.
- **"Remember this device" / trust window for 2FA.** Explicitly not used (`trustDevice` is not enabled); the second factor is required on every sign-in.
- **A self-serve way to disable or switch 2FA method.** Not built in V1; 2FA is mandatory and cannot be turned off. A future settings surface to switch method is noted as buildable later without rework, but does not exist today.
- **Quota enforcement, spend caps, or a circuit breaker on AI usage.** The AI usage tracking design is explicitly observe-only: no soft or hard caps, no per-org limit configuration, and no customer-facing or org-admin usage UI in V1. The go-live checklist lists rate-limiting the AI request surfaces, a per-org quota, and an assistant spend cap/circuit breaker as unresolved pre-launch items; today there is no bound of any kind on AI request volume.
- **Enforcement of the small-cell (Article 9) masking minimums in-app.** The gap engine's in-app view uses a loose 1-woman/1-man floor because HR already sees every individual salary; the stricter 4-person/2-per-gender masking is planned only for the future export boundary (M8), not built.
- **Export/access logging for kartläggning views.** ADR-0011 decided views and exports of a pay-mapping should be logged at the export boundary; this is not implemented yet (tracked in the go-live checklist, "Modul 8/9").
- **An erasure hook for samverkan (collaboration) participant names or for person/pair-targeted pay-mapping actions and notes.** Both are explicitly undecided go-live items: free-text participant names and action/note text can name an employee, and no erasure or anonymization path reaches either table today.
- **Scrubbing of email addresses embedded in older, un-launched-at-the-time audit payloads.** Documented in ADR-0009 as a V1 limitation, since resolved: the invitation events that were the only source of such payload PII (`invitation.created`/`accepted`/`revoked`) ship with id/code-only payloads, so there is nothing left to scrub in current code.
- **A cross-org email index for the `users` mirror used only for admin-page convenience filters** was floated and dropped: email uniqueness is enforced only in Better Auth, and the mirror's `by_email` index exists solely for the bootstrap path, not general lookup.
- **Enterprise SSO/OIDC.** Explicitly deferred from the CRA hardening batch as a separate, larger design effort (also noted in ADR-0001 as incompatible with the Better Auth component's Local Install setup today).
- **A strict, enforcing, nonce-based Content-Security-Policy.** The CRA hardening batch ships CSP as Report-Only only, specifically because a strict policy would need a per-request nonce threaded through `proxy.ts` and could silently break Next.js hydration or the Convex WebSocket connection; the enforcing version is a flagged follow-up.
- **Formal governance docs** (subprocessor/DPA register, incident-response/breach-notification runbook, audit-log retention and access policy). Deferred from the CRA hardening batch because they need facts only the business can supply (signed DPAs, retention periods, an IR owner).
