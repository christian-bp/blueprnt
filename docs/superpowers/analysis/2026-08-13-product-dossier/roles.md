# Roles dossier

## Behavior today

**Role register (`/roles`).** Route: `apps/dashboard/app/(app)/roles/page.tsx`; table component `apps/dashboard/components/roles/roles-table.tsx`. A single `@tanstack/react-table` grouped by role family: each family is a group header row (name links to `/roles/families/[familySlug]`, role count), followed by its role rows; "No family" renders last. Columns: title (link), track, team, and level (merged in from `assessment.results.getResults`, since level lives with results, not with `listRoles`). No per-column sorting (grouping is the order) and no pagination. Free-text search matches title + team + function, case-insensitive substring, via a pure exported `globalFilterFn`. A result counter ("N of M roles") shows only while a search/filter is active. Header actions: "New role" (outline, opens `CreateRoleDialog`) and "Add roles with AI" (filled, links to `/roles/import`) — import is the primary action, matching the people page's hierarchy (`docs/superpowers/specs/2026-08-01-in-app-ai-role-import-design.md`). Zero roles renders `Empty`.

**Role families.** Backend `packages/backend/convex/assessment/families.ts`: `roleFamilies` table (`orgId`, `name`, `slug`), `createRoleFamily`/`renameRoleFamily`/`removeRoleFamily`/`listRoleFamilies` as `orgMutation`/`orgQuery` (member scope, not admin-gated). `familyId` on `roles` is optional; a role belongs to at most one family. Removing a family clears `familyId` on its roles (they are never archived or deleted) and deletes the family row (hard delete is safe: families carry no derived data). Name uniqueness is case-insensitive on the trimmed name (`errors.roleFamilyExists`). Family page: `apps/dashboard/app/(app)/roles/families/[familySlug]/page.tsx`, actions via `apps/dashboard/components/roles/family-actions-menu.tsx` (Rename via `rename-family-dialog.tsx`, Delete family). The delete confirm dialog lists the affected roles by title so the "roles get unfiled, not deleted" consequence is explicit (`docs/superpowers/specs/2026-06-29-role-pages-restructure-design.md`). The family page groups roles per track (track order), ordered by level order, and shows each role's level key, status/progress, and result — the same visibility rule as the results view (values only for complete roles; blindness unaffected). Families never touch scoring: adding/removing a family cannot change a derived level (`packages/core` untouched).

**Role detail page.** Route: `apps/dashboard/app/(app)/roles/[roleSlug]/page.tsx`; queries `assessment.roles.getRoleBySlug` and `evaluationModel.model.getModel`. Header is a `PageBreadcrumb` (Roles > Family > Role, family crumb omitted for a family-less role) plus the track badge and an archived badge. Layout (current): `grid gap-6 lg:grid-cols-3`, `RoleProfileCard` at `lg:col-span-2` on the left, `RoleEvaluationCard` in a sticky right rail (`lg:sticky lg:top-6 lg:self-start`); `RolePeopleCard` (the holder list) renders full width below the grid. This is the layout as of the current codebase; earlier specs (`2026-06-29-role-page-evaluation-layout-design.md`) describe a full-width stacked "evaluation-first" layout that was later reverted back to the two-column grid with a sticky rail — treat those specs as design history, not current behavior.

**Role profile card** (`apps/dashboard/components/roles/role-profile-card.tsx`): read mode shows title, function, team, track, family, purpose, responsibilities. It owns its own `editing` state and its own `...` dropdown menu (Edit; Archive for admins on a non-archived role — the empty-menu rule hides the trigger otherwise). Edit mode shows an AI-draft trigger (a `MorphPopover`, sparkle icon) next to Cancel/Save. The AI draft (`draftRoleProfile` action) fills the purpose/responsibilities fields in the local draft only; nothing persists until Save, which calls the normal `updateRole` (audited as a manual edit, only changed fields patched). Archived roles are fully read-only (no Edit, no AI, no rating).

**Job profile fields.** Schema (`packages/backend/convex/assessment/tables.ts`): `roles` carries `orgId`, `title`, `slug`, `function`, `team`, `trackKey`, `familyId?`, `purpose`, `responsibilities`, `archivedAt?`, `anchorRole?`. There is no `status` field (draft/inReview/approved) in the current schema or `getRole`/`getRoleBySlug` projection — only `archived: boolean`. `PROFILE_TEXT_FIELDS = ["purpose", "responsibilities"]` (`packages/backend/convex/assessment/roles.ts`); the seven previously-optional structured fields (`decisionMandate`, `stakeholders`, `knowledge`, `financial`, `people`, `risk`, `deliverables`) were deleted end to end pre-launch (`docs/superpowers/plans/2026-06-13-slim-role-profile.md`). `isProfileComplete(role)` requires both `purpose` and `responsibilities` non-empty after trim; this gates rating.

**Evaluation card** (`apps/dashboard/components/roles/role-evaluation-card.tsx`), titled "Evaluation": a state machine keyed on `evaluated = totalCriteria > 0 && ratedCount === totalCriteria`. Progress view (not evaluated, not archived): progress text plus a Rate/Continue CTA to `/roles/{slug}/rate` when the profile is complete, or the stated precondition ("fill in purpose and responsibilities...") when it is not. Result view (evaluated, not archived): the weighting (0–100), the level badge, "Level 1 is highest" note, `RoleCriterionBreakdown` (per-criterion contribution share, sorted descending: `contribution_i = value_i * weightPoints_i`, `share_i = contribution_i / sum(contribution)`, bar fill normalized to the top driver while the printed percentage is the true share; all-zero ratings yield all-zero shares with no division by zero; `packages/core/src/scoring.ts` `criterionShares`, `docs/superpowers/specs/2026-06-18-role-result-contribution-breakdown-design.md`), and a trailing `...` actions menu (`MoreHorizontalIcon`) holding "Adjust ratings" (links to `/roles/{slug}/rate`, everyone) and, for admins, "Manage anchor role" / "Designate as anchor role" (opens the anchor dialog). An anchor status row (heading, help, status badge, level badge, motivation) renders inline in the body, separated by a divider, whenever the role is an anchor — visible to everyone, but only the designate/manage action is admin-gated. Archived roles show read-only progress text, no CTA, no menu.

**Anchor roles.** Backend `packages/backend/convex/assessment/anchorRoles.ts`. `designateAnchorRole` (admin only) requires: role exists in org, not archived (`errors.roleLocked` otherwise), not already an anchor (`errors.invalidTransition` otherwise), and a COMPLETE assessment (every criterion rated, so a computed level exists; `errors.ratingsIncomplete` otherwise). Stores `{ expectedLevel, motivation, status: "active", reviewedAt }` as an aggregate on the role doc (never a separate table row is deleted — status moves to `"replaced"` instead, e.g. on archive, so calibration history stays auditable). `updateAnchorRole` lets an admin edit level/motivation/status; `listAnchorRoles` (admin) returns all anchors with their live computed level next to the agreed one, excluding archived roles. UI guidance: "2 to 5 anchor roles in total is usually enough" (`countHint`); a soft warning ("tooMany") appears once 5+ active anchors exist, but nothing in the backend enforces a hard cap.

**Role people/holder list** (`apps/dashboard/components/roles/role-people-card.tsx`, `RolePeopleCard`): a read-only, paginated (25/page) table of the employees currently classified into this role — the reciprocal of the person page's role link. Columns: name (link to the person), seniority badge, department, FTE. This is Role != Person data read live from the people context; the role tables never carry it.

**Role track change.** `updateRole` accepts a changed `trackKey`. Because seniority ladders are disjoint per track (IC1–IC5, Lead-1..3, M1–M3), every active person-assignment holding a level invalid for the new track is reset: the engine's `suggestSeniorityForPerson` re-suggests a seniority for the new track and `writeAssignment` rewrites the assignment with `levelSource: "suggested"` (unconfirmed) — including a previously CONFIRMED seniority, since a confirmation from the old track's ladder is meaningless on the new one. The mutation returns `{ senioritiesReset }` (verified against `updateRole`'s `returns` validator in `packages/backend/convex/assessment/roles.ts` and its use in `role-profile-card.tsx`, which reads `result.senioritiesReset`) so the UI can show a specific toast. The formerly-blocking `errors.roleTrackChangeBlocked` error code was removed (ADR-0005's addendum, 2026-08-05): a track change no longer blocks, it resets and re-confirms.

**In-app AI role import** (`/roles/import`, `apps/dashboard/components/roles/import/role-import-wizard.tsx`): a full-screen wizard, purely additive — never renames, archives, or re-tracks anything existing. Paste-only textarea (max 20,000 chars, `MAX_STARTER_IMPORT_TEXT`), the AI groups pasted roles into families (reusing an existing family name case-insensitively when it matches), then a review screen shows the org's WHOLE register as one table grouped by family: existing roles render read-only (no input, no drag handle, no remove control — "everything removable on this screen is something that does not exist yet"), proposed roles are editable rows with title input and track select. A proposed role whose title an existing (or another proposed) family already has is dropped before the review renders (never becomes a row) and is counted as "already existed". Confirm calls `confirmRoleImport`, backed by `insertAdditiveRoles`, which validates the whole payload before any write (`errors.roleFamilyExists` for a name collision, `errors.notFound` for a bad `familyId`) then inserts new families and roles, and schedules `prefillRoleProfiles` scoped to just the created role ids (so an in-app import of 3 roles does not draft profiles for every empty-profile role in the org). Caps: `MAX_FAMILIES = 20`, `MAX_ROLES = 100`, `MAX_FAMILY_NAME = 100`, `MAX_ROLE_TITLE = 200` per import payload (`packages/constants/src/starterSet.ts`). Reserved role slugs: `"import"` and `"families"` cannot be used as a bare role slug (they fall through to the prefixed/short-id form), because `/roles/import` and `/roles/families` are static routes that would otherwise shadow a role.

**Archiving.** `archiveRole` (admin only) sets `archivedAt`; this is the ONLY status-like lifecycle action left on a role (no unarchive mutation exists — archive is one-way). An archived role becomes read-only everywhere (profile edit, AI draft, rating, anchor designation) and its anchor status (if any) is set to `"replaced"` rather than deleted.

**Role sheet (quick-look).** `apps/dashboard/components/role-sheet.tsx`: a `RoleSheetProvider`/`useRoleSheet()` context mounted once in the app shell, opened by clicking a `RoleChip` in the Overview's band ladder/matrix (`apps/dashboard/app/(app)/work/page.tsx`). Read-only right-side `Sheet`: header (title, track badge, status/archived/anchor/deviation badges), result block (weighting + level badge + `RoleCriterionBreakdown` when complete, or progress-only when incomplete — no per-criterion values pre-completion, preserving blindness), profile prose, and a footer "Open role" link to the full page. No editing, AI, status workflow, or anchor designation in the sheet.

**Anchor role vs anchor role designation UI evolution.** The standalone `AnchorRoleCard` (a permanent card below the Evaluation card) was replaced by a compact `RoleAnchorControl`/`RoleAnchorStatus` + `AnchorDialog` pair rendered inside the Evaluation card, then the designate/manage trigger moved again into the card's `...` actions menu while the status row (when designated) stayed inline in the card body. The file is still named `role-anchor-control.tsx`.

## Terms and history

- **Role (Roll)**: a job/position being evaluated, defined by its content, requirements, responsibilities, and impact — never by the person holding it. A role has a title and a track; seniority sits on the individual, not the role (ADR-0005). If a senior's actual work differs, that becomes a separate role. Avoid: "level role" (Nivåroll, deprecated), Person/Employee/Individual (explicitly NOT a role).
- **Job profile (Jobbprofil)**: the standardized description required before evaluation. Mandatory core: identity (title, function/department, team, track) plus purpose and responsibilities. The seven previously-optional structured fields (decision mandate, stakeholders, knowledge requirements, financial responsibility, people responsibility, risk/consequence, deliverables) were deleted pre-launch for simplicity; they can return later without migration cost.
- **Role family (Rollfamilj)**: a content-grouping entity (e.g. "Software Engineering", or as broad as an organization wants). Optional membership, never "job family" (jobbfamilj). Families never affect scoring.
- **Track (spårtyp, e.g. IC/Lead/Manager)**: the kind of job the role is. Sits on the role, unchanged by ADR-0005.
- **Seniority (Senioritet, code `seniority`)** — renamed by ADR-0014 from the old term "Nivå" (also historically "Level" in `track-level-band.md`): the INDIVIDUAL's seniority within the role's track (e.g. IC1–IC5, Lead-1–Lead-3, M1–M3). Set on the person's assignment (V2 people context), never on the role. Numbered with 1 as lowest within a track ladder (IC1 lowest, IC5 highest) — the opposite direction from Level.
- **Level (Nivå, code `level`)** — renamed by ADR-0014 from the old term "Band" (English "Band" in `track-level-band.md`): the ROLE's computed weight/outcome, derived deterministically from the score via the level thresholds. Level 1 is highest (lower level number = heavier role). Never set manually; always the deterministic outcome of ratings + model via `deriveResults`/`assignLevel` (`packages/core`).
- **Step (Steg, code `step`)** — renamed by ADR-0014 from "anchor scale levels" (`anchors[].level` in code became `anchors[].step`): a criterion's six positions on the 0–5 assessment scale (UI label "bedömningsskala" / "assessment scale"), never confused with the criterion's 1–5 weight point or with seniority.
- **CRITICAL BOUNDARY**: ADR-0014 renamed three previously-collided terms — the old "Band" (role's computed weight) is now "Level"; the old "Nivå"/"Level" (individual's seniority) is now "Seniority"; the old "levels" on the anchor/assessment scale are now "Steps". Pre-ADR-0014 documents (ADR-0002, 0004, 0005, 0011, 0012, `track-level-band.md`) keep the OLD words as historical record and were never rewritten — read them with this translation key: their "Band" = today's Level, their "Level"/"Nivå" (on the individual) = today's Seniority.
- **Anchor role (Ankarroll)**: a chosen internal reference role with an agreed level, used to sanity-check other roles' evaluations AFTER ordinary criterion rating (decision support, never a verdict). Distinct from an "anchor" (ankare) — a criterion's 0–5 text, called "assessment scale" in the UI. 2 to 5 anchor roles total is the usual guideline for small/medium orgs (soft UI hint, not a hard cap).
- **Role placement (Rollplacering, V2 term)**: connecting an employee to a role and giving them a seniority within the role's track. Belongs to the people context, never to assessment; "placement" is reserved for this and never used for a role's level outcome.
- **Assessment/Rating/Motivation/Score**: see the evaluation section's glossary; roles carry the object being scored, not the scoring mechanics.
- **ADR-0005 (accepted 2026-06-07)**: a role bears only a track, never a level. This revised the source document `track-level-band.md`, whose "level roles" model ("Software Developer - IC2" as its own role) is superseded. The Swedish pay-mapping "equal work" group is the role; splitting into level-roles created artificial subgroups that didn't match how the analysis is actually done. The escape valve: if a senior's work genuinely differs, the org models it as its own role — role granularity is the organization's choice.

## Rationale

- **Roles carry track, not seniority** (ADR-0005): matches Swedish pay-mapping practice (DO's guidance), where the "equal work" group is the role — all people doing essentially the same job form one group, work evaluation happens per group, and seniority explains within-group pay differences. Level-roles split that group artificially. Also simpler setup: one job is one role, not five.
- **Level is always derived, never overridden** (ADR-0002, `docs/contexts/assessment/CONTEXT.md`): the role's level outcome is always computed from stored ratings via the current model; there is no manual override anywhere. To change a level, adjust ratings or the model (criteria/weights/thresholds), never the individual role's outcome. This strengthens objectivity and is supported by live recompute + the audit log.
- **Anchor roles calibrate AFTER rating, never replace criterion rating** (`docs/contexts/assessment/CONTEXT.md`): decision support only; a designated anchor requires a complete assessment because it needs its own criteria profile and computed level to be useful as a reference.
- **Role families are presentation-only, deliberately not entities that affect scoring** (`docs/superpowers/specs/2026-06-06-role-families-design.md`): this reverses PLAN-V1 §9.14's original "not modeled as its own entity in V1" decision, recorded via the glossary + PLAN rather than a new ADR, since it is a data-model evolution, not an architecture invariant.
- **The seven structured job-profile fields were deleted for simplicity** (`docs/superpowers/plans/2026-06-13-slim-role-profile.md`): fewer fields to fill in before evaluating; they can be reintroduced without migration cost since removing optional fields never breaks stored data.
- **The AI role import is purely additive and never destructive** (`docs/superpowers/specs/2026-08-01-in-app-ai-role-import-design.md`): unlike onboarding's whole-org starter-set flow (which can archive roles missing from the payload), the in-app equivalent must never retire an existing register just because a pasted list omitted a role.
- **Track change resets rather than blocks affected seniorities** (`docs/superpowers/specs/2026-07-12-role-track-change-design.md`, and ADR-0005's 2026-08-05 addendum): seniority ladders are disjoint per track, so a track change makes every existing seniority invalid; blocking the change entirely was replaced with an automatic re-suggest + re-confirm flow, surfaced through the same "Suggested" badge and dashboard to-do machinery already used for other unconfirmed seniorities.
- **Role id is permanent, never reused** (`docs/contexts/assessment/CONTEXT.md`, CLAUDE.md): a re-evaluation changes ratings/score/level but never the role's identity, because V2's equal/equivalent-work grouping in pay-mapping depends on stable role identity.
- **Role != Person is a hard boundary** (`docs/contexts/assessment/CONTEXT.md`, CLAUDE.md): the `roles`/`ratings` tables must never carry person, salary, or performance fields; the holder list (`RolePeopleCard`) reads live from the people context instead of storing anything on the role.

## Edge cases and error states

- **Profile incomplete blocks rating**: a role cannot be rated until `purpose` and `responsibilities` are both non-empty (trimmed); the Evaluation card states this precondition in words rather than hiding the CTA silently.
- **Archived role is read-only everywhere**: no Edit, no AI draft, no rating CTA, no anchor designation/management menu item, no card actions menu at all in the complete state (the menu itself is only rendered when not archived). Mutating an archived role throws `errors.roleLocked` ("This role is approved and locked. Reopen it first." — note the message text predates the status-field removal and still references "approved"; there is no unarchive path today).
- **Duplicate role title within a family** throws `errors.roleExists` ("A role with that name already exists in this family."); the uniqueness check (`assertUniqueRoleTitle`/`roleTitleKey`) is case-insensitive, scoped to the family, and ignores archived rows — so an archived role with a matching title does NOT block a fresh active one.
- **Duplicate family name** (case-insensitive, trimmed, per org) throws `errors.roleFamilyExists` ("A family with that name already exists.") — this also fires from the AI import's family creation and from onboarding's starter-set creation.
- **Anchor designation preconditions**: not found (`errors.notFound`) if the role doesn't exist in the org; `errors.roleLocked` if archived; `errors.invalidTransition` if already an anchor; `errors.ratingsIncomplete` ("All criteria must be rated first.") if the assessment isn't complete yet (no computed level).
- **Anchor status never disappears, only becomes "replaced"**: archiving an anchor role (or any invalidating action) moves its status to `"replaced"` rather than deleting the aggregate, so calibration history stays auditable; `listAnchorRoles` excludes archived roles from the admin list, but a replaced-status role still carries its history.
- **Track change with active assignments**: resets every active person-assignment whose seniority is invalid for the new track (in practice all of them, since ladders are disjoint), including a previously CONFIRMED seniority — the UI shows a specific toast naming the count reset; a role with no active assignments returns `senioritiesReset: 0` with no side effects. Closed/historical assignments are never touched.
- **Family deletion**: unfiles (not deletes/archives) every role in the family; the confirm dialog lists affected role titles; an empty family shows no list.
- **AI role import edge cases** (`docs/superpowers/specs/2026-08-01-in-app-ai-role-import-design.md`, `...review-register-design.md`): leaving mid-generation dismisses the open suggestion on next entry (nothing resumes); leaving mid-review prompts a discard confirm; every proposed role already existing renders all rows muted with Create disabled and an explanation; generation failure shows a preserved-textarea alert with retry; two tabs importing concurrently rely on the skip rule for overlap, but a genuine new-family name collision surfaces `errors.roleFamilyExists` in review; an org with no evaluation model cannot reach this flow in-app (onboarding always creates one first).
- **Reserved slugs**: a role titled "Import" or "Families" cannot claim the bare slug `import`/`families` (falls through to the prefixed or short-id form), since those are static route segments under `/roles/`.
- **Errors namespace keys this section's surfaces can raise** (verified by grep against throw sites): `errors.notFound` (role/family/suggestion not found or wrong org), `errors.invalidInput` (profile field over the length bound, `MAX_ROLE_PROFILE_FIELD = 5000`, or an empty/over-length title, `MAX_ROLE_TITLE = 200`), `errors.roleLocked` (archived role blocks edit/rate/anchor/AI-draft/import-related writes), `errors.roleFamilyExists` (duplicate family name, case-insensitive), `errors.roleExists` (duplicate role title within a family), `errors.invalidTransition` (re-designating an already-designated anchor), `errors.ratingsIncomplete` (anchor designation on an incomplete assessment; also thrown generally when a level is required before it exists), `errors.invalidSeniority` (a seniority invalid for the role's track — surfaces in person-assignment writes triggered by role/track changes), `errors.adminRequired` (archive, anchor designate/update, and other admin-only role mutations attempted by a non-admin), `errors.aiUnavailable` / `errors.aiGenerationFailed` (the AI profile draft and the AI role import generation).

## Deliberately absent

- **Level (weight) override**: there is no manual override of a role's level anywhere; the brief that originally proposed a documented-reason manual adjustment was deliberately dropped (`docs/contexts/assessment/CONTEXT.md`, "Flaggade oklarheter"). To change the outcome, change ratings or the model.
- **Level-per-role (career-step banding per level on the role)**: removed from V1 by ADR-0005; a role gets one level regardless of which seniorities staff it. The old level-per-track guardrail min/max ranges are also out of V1 (`checkGuardrails` removed from the engine, `trackGuardrails` table removed from schema); they remain only as reference data in `standardmall.md` for possible V2 reuse.
- **Family-level analytics, reordering/merging families, drag-and-drop family management, family descriptions/metadata beyond the name, and track/level progression EDITING from the family page**: all explicitly out of scope in the role-families spec (view-only progression).
- **A separate "Create role" button once the AI import review shows the whole register**: `CreateRoleDialog` is slated to be dropped from the roles page once drag-into-a-real-family lands in review (already partly landed); it survives only on the family page, where the family context is fixed.
- **File upload (CSV/XLSX) or an industry-template path in the in-app AI role import**: paste-only, no file input, no template — those exist only in onboarding's separate flow.
- **Unarchive**: no unarchive mutation exists; archiving a role is one-way. Adding it would be a new backend mutation, explicitly deferred.
- **Cascading archive on family delete**: rejected — a role is an independent evaluable unit not contained by its family, so deleting a family only unfiles its roles, never archives them.
- **Cross-track seniority mapping on a track change**: no mapping from e.g. IC3 to a specific Lead level; the ladders are independent, so track change re-suggests from the person's own signals and requires human reconfirmation.
- **Reordering/status workflow (draft/inReview/approved) on a role**: present in earlier specs and plans (`role-detail-page-redesign-design.md` refers to "approved roles locked") but absent from the current schema, which carries only `archivedAt`; the only lifecycle state left is active vs archived.
- **URL deep-linking or browser-back-to-close for the RoleSheet**: no `?role=` param, no intercepting routes; the opener is in-memory state only.
- **Hard cap on anchor role count**: the 2-5 guideline is a soft UI hint (`tooMany` warning text), never enforced by the backend.
