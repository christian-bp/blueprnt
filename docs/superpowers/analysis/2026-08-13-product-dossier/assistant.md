# Assistant section dossier

## Behavior today

**Overview prompt block.** The overview page (`apps/dashboard/app/(app)/page.tsx`) renders `AssistantPrompt` (`apps/dashboard/components/assistant/assistant-prompt.tsx`) inside its hero, above the existing todo/widgets/chart content, which stays unchanged below it. The hero also shows a status line (`components/overview/overview-status-line.tsx`) rendering `dashboard.overview.todoSummary` (rich/ICU, linking to the todo section) when the user has outstanding todos, or `allCaughtUp` otherwise. Submitting the overview prompt sends a message with `fresh: true`, which archives any active thread before creating a new one, then navigates to `/assistant` where the reply is already streaming.

**The `/assistant` page.** `apps/dashboard/app/(app)/assistant/page.tsx` is a full-width, viewport-bounded route (the `AppShell` skips its normal max-width and locks the row's height for this route: `assistantBounded`). It renders a left `AssistantHistoryPanel` (collapsible, persisted open/closed via a cookie idiom, `lib/assistant-history-state.ts`) and a right chat column with a centered `AssistantTitle` and a "New conversation" action. `useAssistantChat` (`apps/dashboard/hooks/use-assistant-chat.ts`) is the single subscription both the page header and `AssistantPanel` read (Convex dedupes it), so disabling "New conversation" while a reply streams never lags a render behind the panel.

**One active thread per user per org.** `packages/backend/convex/assistant/chat.ts`: `getActiveThread`, `listMessages`, `sendMessage`, `stopGeneration`, `newConversation`, `renameConversation`, `switchConversation`, `deleteConversation`, `listThreads` are all `orgQuery`/`orgMutation`. `sendMessage` inserts the user message plus an empty "streaming" assistant placeholder in the same transaction, then schedules `internal.assistant.generate.generateAssistantReply`. Only one thread is "active" at a time per (org, user); starting a new conversation archives (not deletes) the old one. A message cannot be sent while the active thread's last message is still "streaming" (`errors.assistantBusy`).

**Streaming.** `packages/backend/convex/assistant/generate.ts` is a `"use node"` internal action that runs AI SDK v7 `streamText` against Mistral, with `assistantSystemPrompt` (`assistant/knowledge.ts`) as the system prompt and up to `ASSISTANT_MAX_TOOL_STEPS` (3) tool-calling steps. It folds the stream's parts into the placeholder message's `parts` array via `internal.assistant.chat.updateParts`, flushed at `ASSISTANT_FLUSH_INTERVAL_MS` (40ms in current code; the original plan and ADR text describe 250ms, since revised by the iteration-2 work). Clients get streaming purely through Convex reactivity (`useQuery`), no websocket or SSE of their own. `stopGeneration` sets a cooperative `stopRequested` flag on the message row; `updateParts` checks it (and checks the message is still "streaming") on every flush and returns `true` to tell the action to stop writing.

**Messages are typed parts, not plain text.** `assistant/tables.ts` defines `assistantMessagePart` as a Convex-validated union of `{ type: "text", text }` and `{ type: "chart", chart: assistantChartKind, summary }`, so an unknown part kind cannot be stored. A chart part stores only the chart's kind and the model-facing summary sentence; it never stores a data series. The client renders a chart from **live** org data by reusing the overview's own chart components (confirmed: `apps/dashboard/components/assistant/assistant-chart-part.tsx`, `widget-viz.tsx`), so an old conversation's chart always shows current data.

**Tools (all read-only, org-scoped).** `packages/backend/convex/assistant/tools.ts` exposes four tools to the model: `get_org_stats`, `get_pay_stats`, `show_headcount_trend`, `show_pay_gap_trend`. `get_org_stats` and `get_pay_stats` return numbers only (no chart); `show_headcount_trend`/`show_pay_gap_trend` are mapped via `VISUAL_TOOL_CHARTS` (`show_headcount_trend` -> `"headcountTrend"`, `show_pay_gap_trend` -> `"payGapTrend"`) to append a chart part. `get_org_stats`'s workforce size and pay-gap figures come from the latest completed pay mapping's frozen data; its role counts come from the live roles register (these two bases can disagree and the code comment flags this explicitly). `get_pay_stats` reads the live register as of the call time (`asOf: Date.now()`).

**Titles, rename, delete, history.** Beyond the original chatbot plan, the shipped code (iteration 2 and later) adds a generated conversation title (`assistant/title.ts`, small model, generated once per thread, best-effort and never blocking the reply), a manual `renameConversation`, a `deleteConversation` (with a batch-deletion internal mutation `deleteConversationBatch`), and `listThreads` backing the `AssistantHistoryPanel` (a persistent side panel, not the dropdown menu the original design doc sketched).

**Company context.** `sendMessage` resolves `orgSettingsRow` (extracted from `ai/suggest.ts`'s `requireCompleteSettings` lookup, `lib/orgSettings.ts`) and passes industry/country/employeeCount into the prompt when present; unlike the model-draft flows, the assistant does not require complete settings to work.

**Locale.** Every generation resolves its output language via `promptLocale(locale, settings.language)`, the same helper the rest of the AI surfaces use, so responses render in the caller's current display locale.

**Erasure.** `assistant/erase.ts`: `eraseAssistantDataForUser` hard-deletes a user's threads and messages child-first in bounded batches of `ERASE_BATCH` (200), rescheduling itself until nothing remains; called from the user-erasure paths (`eraseUser`/`eraseSelf`/platform `deleteUser`).

**Embedded (non-chat) AI surfaces feeding this section:**
- **Job profile AI draft** (`apps/dashboard/components/roles/role-ai-panel.tsx` over `draftRoleProfile`, `packages/backend/convex/ai/draft.ts`): visible only in the role's edit mode; a MorphPopover with an optional guidance input and a Generate button fills the purpose/responsibilities textareas client-side; the user still saves via the normal `updateRole`. No suggestion-table row for this flow.
- **Criterion compliance AI draft** (`apps/dashboard/components/model/criterion-compliance-dialog.tsx`, confirmed in code at line 83 `useAction(api.ai.draft.draftCriterionCompliance)`): a "Draft with AI" button in the compliance dialog overwrites all six fields (purpose, whyRelevant, overlapNotes, biasRisk, biasComment, biasAction) via per-field `setValue(..., { shouldDirty: true })`; absent when the criterion is locked (`status === "approved"`); after a fill the dialog shows a review note before an explicit approve is required (confirmed at dialog.tsx line 349).
- **In-app AI role import** (`apps/dashboard/app/(app)/roles/import/page.tsx`, confirmed in code): a full-screen wizard (paste -> generating -> review -> prefilling -> done) that groups pasted role text into role families via the AI, purely additive (never archives or renames existing roles), skips duplicate titles rather than rejecting them, and prefills job profiles only for the roles it created (`prefillRoleProfiles` with a `roleIds` scope).
- **Onboarding model/profile assist**: criterion drafts and weight-review suggestions in the onboarding model step, and automatic (non-blocking) profile prefill for new/renamed roles when advancing past the roles step (`ADR-0003` addenda).

**AI usage telemetry.** Every generation (assistant chat, titles, role profile drafts, criterion compliance drafts, model drafts, weight reviews, starter/role imports) writes an `aiUsageEvents` row and upserts a per-org-per-month `aiUsageMonthly` rollup, via `recordAiUsageDirect`/`recordAiUsage` (`packages/backend/convex/ai/usage.ts`). The assistant chat kind is `"assistant.chat"`; titles are `"assistant.title"`. A stopped generation is still recorded if the provider reported token totals (raced against a short timeout after abort).

**Admin AI usage page.** `apps/dashboard/app/(app)/admin/ai-usage/page.tsx` (confirmed in code): a platform-admin-only route (`platformQuery`/`requirePlatformAdmin`) showing, per the design doc: KPI tiles (total cost, calls, tokens, MoM change, active orgs), a ranked horizontal bar chart of cost per org with amber outlier flagging (cost > max(3x median, an absolute floor)), and a per-org sortable table (cost desc default) with a period selector over the last 6 months. Backend: `convex/platform/aiUsage.ts`, `aiUsageMonthly` gains a `by_period` index for the platform-wide read.

## Terms and history

- **AI as embedded assistance vs. AI as chatbot.** ADR-0003 (accepted) originally stated AI is used as embedded assistance in the flow, explicitly "not a chatbot," and PLAN-V1 (E8) repeated "never chatbot." **ADR-0018** (accepted 2026-08-12) supersedes only that clause: the assistant gets its own chat surface, while every other ADR-0003/ADR-0001 invariant (EU-only Mistral, AI actions never touch the deterministic score/level path, no personal data to the model, suggestion-plus-confirmation for any future write) continues to apply unchanged.
- **Suggestion (forslag) vs. interactive draft.** ADR-0003's core pattern is the suggestion layer: AI output is a row with provenance (`source: "ai"`, status `suggested -> confirmed/rejected`) that HR must explicitly confirm, logged via `ai.suggestionConfirmed`/`ai.suggestionRejected`. The 2026-07-10 addendum to ADR-0003 documents a second, deliberately different pattern: "interactive drafts" (`draftRoleProfile`, `draftCriterionCompliance`) return text directly into an edit form; the human reviews, edits, and saves through the ordinary update mutation, so the saved value carries no `source: "ai"` marker and is revisioned as a normal edit, not an AI-suggestion confirmation. The assistant chat is a third pattern again: read-only, telemetry-only, no suggestion row and no audit row at all (see Rationale).
- **Chart part vs. suggestion.** A chart message part is not a suggestion and not a stored data snapshot: it is a typed pointer (`{ type: "chart", chart: <kind>, summary }`) that the client resolves against live data through the app's existing chart components.
- **Provenance in chat.** Chat messages are explicitly "conversational telemetry, not user-initiated changes to auditable domain state" (ADR-0018 point 5): no `logAudit` rows are written for sending, receiving, renaming, or deleting a chat message. This is a deliberate carve-out from the audit invariant, tracked back to the 2026-06-10 AI usage tracking design's "needs ratification" note and folded into ADR-0018 and CLAUDE.md's audit-invariant scope clause ("Append-only telemetry logs... are outside it").
- **ADR-0014 renames** (Band -> Level/Niva, old Niva -> Seniority/Senioritet, anchor-scale positions -> Steps/Steg) are reflected directly in the shipped assistant system prompt (`assistant/knowledge.ts`): "Level: the computed weight grouping of a role. Level 1 is the highest. Never confuse level with seniority." / "Seniority: an individual's seniority within a track. Not part of V1 role evaluation." / "Step: one of a criterion's 0-5 anchor positions." Any pre-ADR-0014 source describing "Niva" as the computed grouping or "band" is describing today's Level; older glossary/spec text should be read through that translation.
- **Weight points / weighting.** The prompt states the point-budget rule verbatim (ADR-0004): "each criterion carries 1-5 weight points under a fixed budget (criteria count times 3, exact sum). Percent shares are derived, never entered." And distinguishes "Weighting (the 0-100 number)" (a role's normalized result, computed, never stored or edited) from weight points.
- **Role vs. person.** The prompt states this boundary directly: "roles describe jobs; people are employees imported on the People page. Evaluation is always about roles, never persons," matching the Role != Person invariant enforced throughout the backend (ADR-0003, GDPR).

## Rationale

- **Why a chatbot at all, and why now.** ADR-0018's context: the product had accumulated several embedded AI surfaces (model drafts, weight review, job profiles, importers) but no free-form place for a user to ask "what is a criterion?" or "how does our pay gap look?" without hunting through help text. The direction changed rather than being bolted on, hence a new ADR rather than a silent violation of ADR-0003 (`docs/adr/0018-assistent-som-chatt.md`).
- **Why the assistant is read-only in V1.** ADR-0018 point 2: "the assistant is reading, never writing." Any future write capability must go through the existing suggestion/confirm flow with provenance, preserving ADR-0003's core guarantee that AI never auto-decides.
- **Why individual rows never leave the internal query, and why a group floor of 3.** ADR-0018 / design doc `docs/superpowers/specs/2026-08-12-assistant-chatbot-design.md`: "an aggregate over a tiny group degenerates into an individual's salary." The floor is `ASSISTANT_MIN_GROUP_SIZE = 3`, described as a recommended starting point, "raising it to 5 is a one-constant change." The design doc frames the boundary precisely as the AI-processor boundary, not the user boundary: HR already sees individual pay in the product; what is forbidden is an individual's data reaching the model.
- **Why return validators are numbers/enums/composed summaries only.** So that a person-shaped field added to a tool's return type is a compile error, not a runtime leak (design doc, "The full guardrail stack"), backed by a source-confinement test (`assistant/pii-guard.test.ts`) that fails CI if any assistant module besides `insights.ts` reads `people`/`payRecords`/`personAssignments`.
- **Why an input-side name screen exists.** ADR-0018 point 2 and the design doc's guardrail stack: before any model call, the incoming message is checked against the org's employee names; a message containing a full employee name is refused with an explanation, and no AI call and no usage row are recorded for it (implemented as `containsEmployeeName` in `assistant/insights.ts`).
- **Why Convex-native, not `@convex-dev/agent` or a Next.js AI SDK route.** The chatbot design doc's Decision 1: the `@convex-dev/agent` component (0.6.4) pins `ai@^6`, incompatible with the backend's AI SDK v7 standardization; a Next.js route handler would split the Mistral key out of Convex and violate "AI calls only in Convex actions" (ADR-0001/0003). The chosen shape (two tables, `sendMessage` orgMutation + a `"use node"` internal action running `streamText`) keeps every invariant structurally enforced and gives durable, cross-tab-shared conversations "for free," unlike midday's client-memory-only chat (verified against the midday reference repo per the design doc).
- **Why charts render by reference, not by snapshot.** Chart parts store only the chart kind because, per the design doc, this "adopts" midday's invoice-canvas pattern (reference + refetch, never render the tool payload directly); it guarantees the model's numeric summary and the user's rendered chart never diverge from live data, and it means no data series is ever duplicated into chat storage (relevant to the GDPR/erasure story too).
- **Why interactive drafts (job profile, criterion compliance) skip the suggestion table.** ADR-0003's 2026-07-10 addendum: the human reviews and edits the text in the form before saving, so the mutation only ever sees the final, human-edited text and cannot know how much of the AI draft survived; a `source: "ai"` marker would therefore be misleading. This is a deliberate, documented divergence from the fully-AI-generated suggestion-layer flows (model draft, weight review, starter/role import), which keep full provenance because nothing is edited before confirmation.
- **Why the onboarding profile prefill is a scoped exception to "nothing applies automatically."** ADR-0003's 2026-06-14 addendum: purpose/responsibilities for new or renamed roles are filled without a blocking per-item confirm step, specifically because the text never touches the deterministic score/level path, remains freely editable afterward, and the per-call usage event plus the resulting `role.updated` audit row already supply the provenance trail.
- **Why the in-app role import is purely additive** and must not reuse onboarding's whole-org reconcile semantics: `docs/superpowers/specs/2026-08-01-in-app-ai-role-import-design.md` explains that onboarding's `reconcileStarterSet` archives every active role not present in the payload, which would silently retire an existing register; the in-app flow instead skips (never rejects) duplicate titles and only ever adds families/roles.
- **Why the audit field-label rules still apply to AI-confirmed rows.** Even though chat itself carries no audit rows, the suggestion-layer AI flows (model draft, weight review, starter/role import) do write `ai.suggestionConfirmed` rows, and CLAUDE.md's coded-value rule forced `AI_KIND_KEY` to become a compile-time-total `Record<SuggestionKind, string>` and required new `familyCount`/`roleCount`/`skippedCount` field labels for `role.import`, closing a gap that had also silently affected `starter.import` and `model.weightReview` (design doc's audit section).

## Edge cases and error states

- **`errors.assistantBusy`** (`ERROR_CODES.assistantBusy`): thrown by `sendMessage`, `newConversation`, and `switchConversation` in `assistant/chat.ts` when the active thread's last message is still `"streaming"`. UI: "Blueprnt AI is still answering. Wait for it to finish or stop it." Fix: wait, or press stop.
- **`errors.assistantRateLimited`** (`ERROR_CODES.assistantRateLimited`): thrown by `sendMessage` when the user has sent `ASSISTANT_HOURLY_MESSAGE_CAP` (30) messages in the trailing hour. UI: "You have sent many messages in a short time. Try again in a little while."
- **`errors.assistantInvalidMessage`** (`ERROR_CODES.assistantInvalidMessage`): thrown by `sendMessage` when the trimmed, length-clamped (`MAX_ASSISTANT_MESSAGE_LENGTH` = 4000 chars) text is empty. UI: "Write a message before sending."
- **`errors.assistantPersonalData`** (`ERROR_CODES.assistantPersonalData`): the input-side name screen result. When a message contains a full employee display name, the reply is finalized as `"failed"` with this error code, without ever calling the model (confirmed: `assistant/generate.ts` line 91 calls `finalize("failed", ERROR_CODES.assistantPersonalData)`; `chat.test.ts` line 295 asserts the message's `errorCode`). UI: "The message seems to include an employee's personal details. Remove them and ask again in general terms." No usage row is recorded for this case (the model was never called).
- **`errors.aiUnavailable`**: thrown from `assistant/generate.ts` when the provider call cannot even start (mapped the same way the job-profile and criterion-compliance draft actions map it), and reused throughout `ai/draft.ts`/`ai/generate.ts` for those embedded surfaces. Surfaces as an inline error banner in the relevant panel/dialog rather than a toast.
- **`errors.aiGenerationFailed`**: thrown/recorded when the model call completes but generation or schema validation fails (`assistant/streamOutcome.ts`, `ai/generate.ts`). Same inline-error treatment.
- **`errors.roleLocked`**: `ai/suggest.ts` line 903, unrelated to chat but shared by the job-profile/criterion-compliance draft context queries: an archived or approved-and-locked target rejects the draft request.
- **Timeouts and caps not surfaced as distinct error codes but gating behavior:** `ASSISTANT_GENERATION_TIMEOUT_MS` (120,000 ms) bounds a generation; `ASSISTANT_MAX_TOOL_STEPS` (3) bounds the tool-calling loop; `ASSISTANT_MAX_OUTPUT_TOKENS` (4096) bounds a reply's length; `ASSISTANT_TITLE_GENERATION_TIMEOUT_MS` (30,000 ms) and `ASSISTANT_TITLE_MAX_RETRIES` (5) bound the best-effort title generation, which never blocks or fails the main reply.
- **Suppressed pay statistic:** `get_pay_stats` returns a group with `suppressed: true`, `averagePay: null`, `medianPay: null` when its count is below `ASSISTANT_MIN_GROUP_SIZE` (3); the system prompt instructs the model to say the group is too small rather than guess, and the composed summary states this in words ("too small to report"). This is a data-shape state, not a thrown error.
- **Empty org data:** `get_org_stats`/trend tools return zeroed/empty results with an honest summary ("No pay mappings yet") rather than inventing numbers, when the org has no completed pay mapping runs.
- **Stopped generation:** pressing stop sets `stopRequested`; the next `updateParts` flush (or the following check) halts writing and the message is finalized as `"stopped"`, keeping whatever partial parts had already been flushed. Usage is still recorded if the provider reported totals before the abort (raced against `ASSISTANT_USAGE_RACE_MS`, 2000 ms).
- **A vanished or already-finalized message row:** `updateParts` treats a missing row or a non-"streaming" status as an implicit stop signal (returns `true`), covering erasure, archival, or a race with a competing finalize.
- **Cross-user access:** `listMessages`/`stopGeneration`/etc. reject with `errors.notAMember`-class errors when a thread's `orgId`/`userId` does not match the caller (thread ownership is per-user, not shared across an org's members).
- **Criterion compliance AI draft, locked state:** the "Draft with AI" button is absent whenever the criterion's `status === "approved"`; the criterion must be reopened first.
- **Role import wizard, "every proposed role already exists":** all rows render muted, Create stays disabled with an explanation, and Start Over returns to the paste screen with the original text intact (no error thrown; a `resolveImportTargets` result with everything flagged as duplicate/colliding).
- **Role import wizard, leaving mid-generation or mid-review:** re-entering the wizard always opens on an empty paste screen; an open `role.import` suggestion row from a previous, abandoned visit is dismissed (`rejectSuggestion`) on entry, so a late-finishing generation cannot resurrect a stale proposal.

## Deliberately absent

- **Write-capable assistant tools.** V1's assistant is read-only; ADR-0018 explicitly defers any future write capability to the existing suggestion/confirm-with-provenance pattern, not a new mechanism (design doc "Out of scope").
- **More chart kinds and drill-downs** (gender distribution, level distribution, per-family aggregates) are named as later, separate work in the design doc's "Out of scope" section.
- **RAG over documentation.** Named explicitly as out of scope for the chatbot's V1 (design doc); this in-app-docs dossier project is itself the groundwork for a later grounding capability, not something the assistant already has.
- **Multi-thread history UI and attachments** were out of scope for the original chatbot plan; the shipped code has since added a history panel and rename/delete (iteration 2+), so this exclusion is partially superseded in practice, but attachments remain absent.
- **Midday-style @mentions and quick-action chips beyond the three starters** were explicitly deferred (design doc).
- **`@convex-dev/agent`** was evaluated and rejected for V1 because it pins AI SDK v6 against the backend's v7 standardization; ADR-0018 notes it will be "reconsidered when the component supports v7."
- **Retention policy for archived assistant threads** is an open, tracked decision, not a shipped behavior: ADR-0018 and the go-live checklist both flag it as "decided before go-live," meaning archived (not yet erased) threads currently persist indefinitely absent a policy decision.
- **A production-grade rate limiter.** The go-live checklist records the current per-user hourly cap as a simple placeholder ("revisit... upgrade to @convex-dev/rate-limiter if real usage shows abuse patterns"), i.e. today's cap is a V1 stopgap, not the final design.
- **AI betygsforslag (AI-suggested ratings) and calibration/bias review of HR's actual ratings.** ADR-0003's original text explicitly defers "sensitive assist" (AI rating suggestions, calibration/bias checks on HR's ratings, copilot) until the core scoring path and blinding are proven; the 2026-07-10 addendum clarifies the criterion-compliance bias review that *did* ship is a different thing (bias review of the criterion's documentation text, not of HR's ratings).
- **A bulk "draft all criteria" action** for criterion compliance was explicitly out of scope; the AI fill is per-criterion, inside the dialog only (criterion-compliance-ai-fill design doc).
- **File upload / industry template input for in-app role import**, and any family-page-scoped entry point: the in-app importer is paste-only and reachable only from the roles page (role-import design doc, "Non-goals").
- **Per-field AI provenance on saved job-profile and criterion-compliance drafts.** Explicitly dropped in favor of usage telemetry as the sole provenance record, because the saved text may have been edited by the human before save (job-profile-ai-fill design doc, "Risks and trade-offs"; ADR-0003 2026-07-10 addendum).
