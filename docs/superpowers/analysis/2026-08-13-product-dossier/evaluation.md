# Evaluation dossier

Feeds docs pages: evaluating-a-role, score-and-levels, adjusting-a-rating, levels-views.

## Behavior today

**Rate a role, one criterion at a time (blind rating stepper).**
Route `apps/dashboard/app/(app)/roles/[roleSlug]/rate/page.tsx` renders `RatingStepper` (`apps/dashboard/components/rating/rating-stepper.tsx`). One criterion per step, in model order; resumes at the first unrated criterion on reopen. Each step shows the criterion's name, description, help text, and its six 0-5 anchor texts as selectable option cards (radiogroup), plus an always-present optional motivation textarea. Digit keys 0-5 select the matching anchor and Enter advances/saves (keyboard shortcuts wired via a document-level listener, disabled while a field has focus). "Next" calls `assessment.ratings.setRating` and only then advances; "Back" moves without saving. The stepper never renders a score, a level, another criterion's value, or any weight as a number anywhere before the result step (assessment glossary's blindness rule, confirmed absent from `rating-stepper.tsx`).

**The result reveal (`RatingResult`, `apps/dashboard/components/rating/rating-result.tsx`).**
Shown after the last criterion. First place score and level become visible. Live query `assessment.results.getRoleResult`; shows `{score} / 100`, a level badge, and (if any active anchor roles exist) a list of anchor roles with their agreed level, plus a "far from anchors" hint when the role's level is 2 or more levels from every active anchor's agreed level (`nearestDistance >= 2`).

**Setting a rating (`assessment/ratings.ts`, `setRating`).**
A 0-5 integer per (role, criterion), optional motivation. Preconditions: role not archived (`errors.roleLocked`), role's job profile complete (`errors.profileIncomplete`), criterion belongs to the org. A no-op write (identical value and motivation) writes nothing and audits nothing. Every write computes `deriveResults` before and after in the same transaction and calls `ctx.audit.levelShifts` (one `level.shift` audit row per role whose level changed, threading the triggering rating as `cause`), then logs `rating.change` with a structured before/after diff of value and motivation.

**Score and level are always derived, never stored (ADR-0002).**
`packages/core/src/scoring.ts`: `scoreRole(ratings, criteria)` = `Math.floor(20 * sum(rating * weightPoints) / sum(weightPoints))`, thrown on an empty criteria array, a duplicate criterion, a duplicate rating, or a rating outside integer 0-5. Ratings for criterion ids not in the current model are ignored (orphan safety). `assignLevel` (renamed from `assignBand` by ADR-0014; see Terms and history)/level-threshold matching (in `packages/backend/convex/evaluationModel` data plus the compute helper) picks the highest threshold at or below the score, Level 1 highest, ties broken toward the lower level number.

**Contribution breakdown (post-completion, per role).**
`RoleCriterionBreakdown` (`apps/dashboard/components/roles/role-criterion-breakdown.tsx`), shared by `RoleEvaluationCard` (role page) and the RoleSheet quick-look. Uses `criterionShares` (`packages/core/src/scoring.ts`): `contribution_i = value_i * weightPoints_i`, `share_i = contribution_i / sum(contribution)`, all-zero when every rating is 0 (no division by zero). Rows sort by share descending (canonical criterion order as tiebreak), animate with Motion `layout="position"` on reweight, and render each criterion's name, contribution-share percentage (bar width normalized to the top driver, the printed percentage is the true share), and motivation text when present. The org-wide weight-points column and the raw 0-5 rating value are NOT rendered here (current code has no `ratingOutOf`/"rated X / 5" string at all: verified absent from `en.json` and from both `role-criterion-breakdown.tsx` and `role-result-card`-successor code). This is a further simplification beyond the original 2026-06-18 design (which specified showing "rated {value} / 5" per row); the shipped surface shows only name + share + motivation.

**Role evaluation card, full lifecycle in one card (`RoleEvaluationCard`, `apps/dashboard/components/roles/role-evaluation-card.tsx`).**
`evaluated = totalCriteria > 0 && ratedCount === totalCriteria`; `showResult = evaluated && !archived`. Three states: (1) not evaluated / progress: an alert if the job profile is incomplete (`profileIncompleteTitle`/`profileIncomplete`), else the "evaluated"/"notEvaluated" line plus a rate/resume CTA to `/roles/{slug}/rate`; (2) computing (`showResult && !result.complete`, a transient state while the query loads); (3) complete: the level as the hero number (`levelNumbered`), a full-width level-position scale bar (one segment per level, the role's level highlighted in the brand color), the score shown as muted secondary text, the anchor icon + deviation badge when the role is an anchor role and its computed level differs from the agreed level, the `RoleCriterionBreakdown`, and a header `...` actions menu (Adjust ratings for everyone; Manage/Designate anchor role for admins only). No standalone inline "Adjust ratings" button remains in the card body (moved fully into the menu per the 2026-06-29 role-page-evaluation-layout redesign).

**Anchor roles (`assessment/anchorRoles.ts`).**
`designateAnchorRole` (admin only): role must exist, not be archived, not already be an anchor, and must have a COMPLETE assessment (every criterion rated, a non-null derived level) before designation; requires an `expectedLevel` (1..levelCount) and a non-empty, length-bounded motivation. `updateAnchorRole` (admin only): reactivating a non-active anchor (`status` -> `"active"`) re-checks archived/complete preconditions; every update bumps `reviewedAt` and audits the role's current computed level alongside the diff. `listAnchorRoles`: excludes archived roles; anchors are never deleted, only marked `status: "replaced"` (via `archiveRole`, which flips any active/underReview anchor designation to `"replaced"` with its own audit row), so calibration history stays auditable. Anchor comparison happens strictly AFTER the ordinary criteria assessment (never a substitute), surfaced in `RatingResult` and in `RoleEvaluationCard`'s inline anchor status row.

**Levels overview (`/work`, `apps/dashboard/app/(app)/work/page.tsx`).**
The route feeding "levels-views": a Ladder view (`LevelLadder`) and a Matrix view (`LevelMatrix`/`FamilyLevelMatrix`) toggle, with a family multi-select filter and a "group by family" switch. `PendingRoles` renders roles whose level is null (assessment incomplete) in a dashed "not yet evaluated" zone; clicking opens the role to continue rating; how far the rating has progressed is deliberately not shown there. The whole view is live-reactive to model and rating changes (ADR-0002).

**Role status: no draft/inReview/approved lifecycle in current code.**
The original evaluation-loop design and plan (2026-06-05) specified a `draft -> inReview -> approved` role status machine with an admin approval step and `errors.invalidTransition` on bad transitions, locking `updateRole`/`setRating` once approved. The current `roles` schema (`packages/backend/convex/assessment/tables.ts`) has NO `status` field at all: only `archivedAt`. `errors.roleLocked` in current code is thrown solely for an archived role (verified in `ratings.ts`, `roles.ts`, `anchorRoles.ts`, `starters.ts`); there is no "approved and locked, reopen it first" behavior in the running app despite that literal string surviving in the `roleLocked` error message. Ratings, and the job profile, stay editable at any time until the role is archived.

## Terms and history

- **Roll (Role)**: the job/position being evaluated, defined by content/requirements/responsibility/impact, never by the person holding it. Has a title and a track; seniority sits on the individual (V2 role placement, ADR-0005), never on the role. Role id is permanent and never reused.
- **Jobbprofil (Job profile)**: the standardized description required before rating: identity (title, function/team, track) plus purpose and responsibilities. The seven structured optional fields (decisionMandate, stakeholders, knowledge, financial, people, risk, deliverables) were deleted pre-launch for simplicity (2026-06-13 plan); can return later without migration cost.
- **Värdering (Assessment)**: the record of evaluating a role against the model: its ratings, computed score, and assigned level, plus motivations.
- **Betyg (Rating)**: the raw 0-5 a rater gives a role on one criterion, judged against that criterion's anchor text. The only hand-entered value.
- **Motivering (Motivation)**: a short free-text explanation of a rating. Always optional, per rating or per role.
- **Poäng (Score)**: the weighted total, normalized to 0-100: `20 * sum(rating * weightPoints) / sum(weightPoints)`, floored. Max is always 100 regardless of criteria count. UI label is "Weighting" (`assessment.score` i18n key); canonical term in speech/code is Score/Poäng. "Viktning" (Weighting) deliberately overlaps in spelling with "viktning," the separate process of weighting criteria with weight points; this is a deliberate product decision, not a term confusion.
- **Nivåutfall (Level outcome)**, formerly Bandutfall/Band outcome, renamed 2026-08-05 by ADR-0014: the level a role lands in, ALWAYS computed automatically from the score via the level thresholds. No manual override exists or ever existed in shipped code; to change the outcome, adjust ratings or the model (criteria/weights/thresholds), never the individual role's level.
- **ADR-0014 rename (2026-08-05, `docs/adr/0014-terminologi-niva-senioritet-steg.md`)**: the computed weight-outcome, formerly "Band" (Nivå in Swedish), is now "Level" (Nivå stays the Swedish word, English changes from Band to Level). The individual's seniority within a track, formerly "Nivå" (Level), is now "Seniority" (Senioritet). The criterion's anchor-scale positions (the six 0-5 rows), formerly "nivå/level," are now "Step" (Steg, code `step`). All pre-0014 documents (including the 2026-06-05 evaluation-loop spec/plan, 2026-06-13 onboarding-role-scoring spec, 2026-06-18 contribution-breakdown spec/plan, and the anchor-role specs from 2026-06-29) use the OLD words: "Band"/"band.shift"/"assignBand"/"BandThreshold" there all map to today's "Level"/"level.shift"/level-threshold code. This dossier translates every such claim into current terms; current code and current i18n confirm the audit event is `level.shift` (not `band.shift`), the score/level object field is `level` (not `band`), and the help/labels say "Level."
- **Ankarroll (Anchor role)**: a designated internal reference role with an agreed level, used to sanity-check other roles' evaluations AFTER their ordinary criteria assessment. Not the same as an **ankare** (a criterion's 0-5 anchor text, called "bedömningsskala"/assessment scale in the UI); always say "anchor role" explicitly to disambiguate. 2-5 anchor roles normally suffice for a small/medium org (backend does not hard-enforce a max, per code read; the "tooMany" hint referenced in the 2026-06-29 spec is advisory UI copy).
- **Bedömningsskala (assessment scale) naming history**: the criterion's six 0-5 anchor texts were called "bedömningsankare" until 2026-06-13, then "bedömningsnivå" until 2026-06-24, then "bedömningsskala" (to avoid confusion with the criterion's 1-5 weight in the weighting step). The scale's six positions are now called **Steg** (Step) per ADR-0014, formerly "nivå." The Convex field name `criteria.anchors` and the i18n key stems (`anchors`, `anchorLevel`, `anchorsLabel`, `anchorsBody`) were deliberately NOT renamed at the code-identifier level (2026-06-13 decision), only the displayed strings changed.
- **AI-förslag (AI suggestion)**: any AI-drafted value (job profile text; AI never drafts ratings), always with provenance and a status lifecycle (generating -> suggested -> confirmed/rejected/failed). HR always confirms; AI never decides and never touches the deterministic score/level path (ADR-0003).
- **Blindness, mitigated by HR-only audience**: because only trusted HR uses the tool, blindness protects against the total anchoring the ratings, not against cheating. Weight points are set in model configuration; during rating entry the rater sees only criteria + anchor texts (no weight points); score and level appear only in the result step, never live during rating.
- **No level override, by design**: the CTO brief mentioned a manual level-adjustment escape hatch; the product deliberately omitted it. The level is always the deterministic outcome (live recompute + audit log per ADR-0002 substitute for that need).

## Rationale

- **Score/level derived live, never stored, no model versioning (ADR-0002, `docs/adr/0002-live-recompute-no-versioning.md`)**: chosen for simplicity and because it fits Convex's reactive model well. Deliberately deviates from the CTO brief's requirement that model changes must not retroactively rewrite historical assessments without versioning; a model change can silently move roles between levels without preserving prior outcomes. Mitigated by the audit log (captures model changes plus which roles' levels changed as a result). Reversing this later (introducing versioning) gets more expensive the more assessments exist; treated as a deliberate V1 shortcut.
- **Weight points 1-5 under a fixed point budget = criteria count x 3 (ADR-0004, `docs/contexts/evaluation-model/viktning-poangbudget.md`)**: raising one criterion's weight requires lowering another's (zero-sum), replacing a hidden 7-level importance scale with Excel weights 8-18. Percent shares are derived display values, never an input.
- **Score formula `20 * sum(rating * weightPoints) / sum(weightPoints)`, floored (`docs/contexts/evaluation-model/standardmall.md`)**: normalizing by the model's own point sum keeps the 0-100 scale meaningful independent of how many criteria exist, so level thresholds keep their meaning when criteria are added or removed. Flooring keeps the comparison against integer thresholds exact.
- **Level thresholds (7 levels, Level 1 highest; `DEFAULT_LEVEL_THRESHOLDS` in `packages/backend/convex/evaluationModel/standardTemplate.ts`, matching `standardmall.md`)**: 98/83/74/63/53/41/0, translating the Excel prototype's thresholds (530/540 etc.) as shares of max. Explicitly flagged as needing calibration against real data before launch; the weight spread changed (5:1 vs. the prototype's 18:8), so the role distribution will not match the prototype's exactly.
- **No manual level override (`docs/contexts/assessment/CONTEXT.md`)**: strengthens objectivity over the brief's suggested manual-adjustment-with-reason escape hatch; deliberately omitted, easy to reintroduce later if ever needed.
- **Anchor roles designated only on a complete assessment (`assessment/anchorRoles.ts`, plus the anchor-role guide referenced in code comments)**: an anchor needs a real criteria profile and computed level to calibrate against; comparison happens strictly after the ordinary rating, as a sanity check, never a substitute for it.
- **Full-screen takeover reserved for single-commit transactions, evaluation stays in normal layout (ADR-0016, `docs/adr/0016-helskarmsflode-eller-vanlig-layout.md`)**: role evaluation autosaves per criterion, so leaving mid-flow leaves a valid partial product (a partially-rated role); it is therefore incremental work, not a transaction, and correctly stays a stepper inside the normal app layout/sidebar rather than a `WizardShell` full-screen takeover (which is reserved for onboarding and the two import flows, where nothing lands in the register until a final commit step).
- **Contribution breakdown surfaces per-role, per-criterion weighting impact (2026-06-18 design)**: the org-global weight-points column is identical on every role and therefore the least informative number to show on a single role's page; the contribution share is the only per-criterion number that is both role-specific and weight-dependent, and it is what visibly reacts when the model is reweighted.
- **Guardrails retired from the rating flow (`docs/contexts/evaluation-model/standardmall.md`, "pensionerade ur V1:s betygsflöde")**: the advisory min/max rating ranges per track-seniority and criterion (curated from the Excel prototype's "Track" tab) are retired from V1's rating flow and kept only as reference documentation (e.g. potential future V2 placement support); verified in code, `checkGuardrails` exists nowhere in current `packages/backend`/`apps/dashboard` call sites, and `trackGuardrails` is not queried anywhere.

## Edge cases and error states

- **`errors.roleLocked`** ("This role is approved and locked. Reopen it first."): thrown today only when the role is archived (`ratings.ts` setRating, `roles.ts` updateRole, `anchorRoles.ts` designate/update, `starters.ts`). The message text still describes the old approval-lock behavior, which no longer exists in code (no role status field); an archived role cannot be rated, updated, or have its anchor designation changed.
- **`errors.profileIncomplete`** ("Complete the company profile first."): thrown by `setRating` when the role's job profile (purpose + responsibilities) is not both non-empty, gating the rating flow. The SAME error code and message string is also thrown elsewhere for the ORG's company profile being incomplete (`ai/suggest.ts`, `ai/prefillData.ts`), a different concept; the shared message text is worded for the company-profile case and may read oddly on a role page.
- **`errors.ratingsIncomplete`** ("All criteria must be rated first."): thrown by `designateAnchorRole` (assessment incomplete, no computed level) and by `updateAnchorRole` when reactivating a non-active anchor whose role's assessment has since become incomplete (e.g. a criterion was added after designation).
- **`errors.invalidTransition`** ("That status change is not allowed."): thrown by `designateAnchorRole` when the role is already an anchor (attempting to re-designate).
- **`errors.invalidInput`**: thrown by `designateAnchorRole`/`updateAnchorRole` for an out-of-range `expectedLevel` or an empty/too-long motivation (max 1000 chars), and by `setRating` for a non-integer or out-of-0-5 rating value.
- **`errors.notFound`**: thrown when a role, criterion, or anchor-carrying role does not exist or belongs to another org.
- **`errors.aiUnavailable`** ("AI is not configured for this environment."): no MISTRAL_API_KEY means any AI action (e.g. role-profile draft) fails with this code; manual entry always still works. Never affects rating itself, since AI never rates (ADR-0003).
- **Incomplete role has no score/level**: a role has a score and level only when EVERY current model criterion is rated (`complete` in `RoleResult`); until then, surfaces show rating progress (ratedCount/totalCriteria), never a partial score. `PendingRoles` on `/work` groups these under "not yet evaluated" and deliberately does not show how far the rating has progressed there.
- **Adding/removing a criterion can flip completeness and levels**: adding a criterion to the model makes previously complete roles incomplete again (an `level.shift` audit row to null); removing a criterion deletes that criterion's ratings (`by_criterion` index) and can make previously incomplete roles complete. The engine additionally ignores any stray rating whose criterionId is not in the current model (defense in depth against orphans).
- **No-op rating write**: submitting the same value and motivation that already exist writes nothing to the database and creates no audit row.
- **Archiving a role that is an active/underReview anchor**: `archiveRole` also flips its anchor designation to `status: "replaced"` (its own audit row), so the role page and audit log agree that an archived role carries no live anchor designation; `listAnchorRoles` excludes archived roles.
- **Anchor "far from anchors" hint**: shown in `RatingResult` when the newly-rated role's level is 2 or more levels away from EVERY active anchor role's agreed level; advisory only, never blocks completion.
- **Anchor deviation badge on the role page**: shown when a role IS an anchor and its live-computed level differs from its agreed (`expectedLevel`) level; the computed level is always primary, the anchor is a sanity check, not the other way around.

## Deliberately absent

- **Model versioning / retroactive-immutability of past assessments** (ADR-0002): a model change silently moves roles between levels with no preserved history of the prior outcome, other than what the audit log records. Explicitly deviates from the CTO brief.
- **Manual level override**: never built. Changing a level requires changing ratings or the model, never the role's derived outcome directly (`docs/contexts/assessment/CONTEXT.md`).
- **Role status/approval workflow** (draft -> inReview -> approved, admin approval, `errors.invalidTransition` on a bad transition): specified in the 2026-06-05 design and plan, absent from the current schema and mutations. Only `archivedAt` gates editability today.
- **Guardrail advisory rating-range hints in the rating flow**: `checkGuardrails`, `GuardrailWarning`, and the seeded `trackGuardrails` per-seniority ranges are retired from the V1 rating UI (kept only as reference data in `standardmall.md`); the rating stepper shows no guardrail hint of any kind.
- **The seven structured job-profile fields** (decisionMandate, stakeholders, knowledge, financial, people, risk, deliverables): deleted pre-launch for information-overload reasons (2026-06-13 plan); could be reintroduced with no migration cost, but are not present today.
- **Per-criterion raw rating value ("rated N / 5") on the completed-role breakdown**: specified in the 2026-06-18 contribution-breakdown design, not present in the shipped `RoleCriterionBreakdown`; only the name, contribution share, and motivation render.
- **Anchor roles / calibration in the original alpha slice**: explicitly out of scope for the first evaluation-loop slice (2026-06-05 design); anchor roles shipped later (2026-06-29 specs) and are covered above as current behavior.
- **CSV/XLSX import/export of roles, motivation-nudge triggers, unarchive UI, AI rating suggestions**: explicitly out of scope in the 2026-06-05 evaluation-loop design; AI never rates in V1 (ADR-0003), consistent with current code (no AI-suggested rating path exists).
- **A dedicated `/results` or `/levels` route**: superseded by `/work` (Overview), which now hosts the Ladder/Matrix level views described under "Behavior today"; the originally spec'd standalone Results page never persisted under that name.
